# WP100 完了レポート — アセット HR1-T テクスチャ差し替え

## 結論

独立画像（PNG / EXR / KTX2）を明示的な `AssetKey` で登録し、HR0 の
`FileWatcher` から WP98 の dependency transaction group を経て GPU テクスチャへ
反映する HR1-T handler を実装した。既存 `registerTexture*` の挙動は変更せず、
`registerReloadableTextureFile` を opt-in 面として追加した。

- extent / format / mip が同じ場合は同じ image と `GlobalTextureId` へ再 upload し、
  image view と material descriptor set を変更しない。
- shape / format / mip が変わる場合は image と参照中 material の descriptor set を
  すべて candidate として作成し、WP98 publish 後に一括 swap する。旧 image、旧 view、
  旧 descriptor set は `RetireSink` から `DeletionQueue` へ移譲する。
- decode、format/capability、candidate image、descriptor allocation のいずれかが失敗した
  場合は publish せず、旧 image / descriptor / logical ID / registry counts / live bytes を
  維持し、`last_reload_error` を更新する。
- watcher gate が disabled の間は handler を呼ばず、実 GPU readback が不変である。

## WP98 接続点との対応

| WP98 の接続面 | HR1-T の実装 |
|---|---|
| `ReloadRequest::key` と `reverseDependents()` | `texture` actor と、その `AssetKey` を依存辺に持つ全 `material-descriptor` actor から group を構成 |
| parse / validate / stage closure | parse で `loadImageFile`、validate で image/SRGB 契約、stage で upload または image + descriptor candidate を作成 |
| `after` edge | 全 material descriptor actor を texture actor の後に固定 |
| `StagedResourceData` | payload、dependency key、compatibility revision、pixel live bytes を返す。stage 中に `declareResource()` は呼ばない |
| frame-boundary publish | 既存 `ReloadCoordinator::applyFrame` を使用し、identity allocator、rollback、barrier、status を再実装していない |
| `RetireSink` | publish 済み payload を確認して live slot を swap し、旧 GPU resource を `DeletionQueue` へ移譲 |

`MaterialContainer` には material 登録時の全 texture binding（組み込み 4/6 binding、
custom texture、split sampler）と texture → material の逆引きを保持する面を追加した。
shape 変更時は使用中 descriptor set を直接更新せず、新しい set を stage して swap する。
これにより in-flight command buffer が参照する旧 set は遅延破棄まで生存する。同一 image を
維持する in-place upload は旧 frame の reader を `waitIdle` で drain してから行う。

## fixture

`texturereload_test` に GPU 必須の 2 ケースを追加し、Vulkan 利用不能時だけ `SKIP()` する。
今回の検証環境では両ケースとも実行され、SKIP はなかった。

1. PNG 1x1 red を登録し、実 image readback が RGBA `(255,0,0,255)` であることを確認。
2. 同 shape の blue PNG へ変更し、同 `GlobalTextureId`、同 image views、descriptor revision
   不変のまま readback が `(0,0,255,255)` へ変化することを確認。
3. 2x1 green PNG へ変更し、image views が交換され、参照 material 全件の descriptor
   revision が 1 増えることを確認。旧 image + 旧 descriptor の pending は 2、
   in-flight frame 経過後は 0。
4. 壊れた PNG は transaction failure となり、view と readback bytes が完全に旧値のまま、
   `failed` と `last_reload_error` が更新されることを確認。
5. 1000 回の同 shape reload に material descriptor actor も参加させ、texture count、
   resource count（texture + material descriptor）、`GlobalTextureId`、descriptor revision の
   差分がすべて 0。registry `liveBytes` は 4 bytes、DeletionQueue pending は 0。
6. gate disabled 中に実ファイルを書き換えても request / GPU capture が不変。その後 gate を
   enabled にして同じ実 FS watcher を通し、PNG overwrite が GPU readback に反映されることを確認。
7. KTX2 を 2x2 / sRGB / 2 mip から 1x1 / UNORM / 1 mip へ変更し、同 logical
   `GlobalTextureId` のまま image/view 再生成、mip 変更、遅延破棄後 pending 0 を確認。

focused 結果は 2 test cases、3053 assertions、全成功。1000 回 + 実 FS 1 回の
`stress.png` reload log 1001 件の所要時間は min 0 ms、平均 1.09 ms、p50 1 ms、
p95 2 ms、max 2 ms。shape 変更 PNG は 2 ms、KTX2 mip/format 変更は 1 ms、
壊れた candidate の拒否は 0 ms だった。

## 手動確認手順

自己完結 project のコード側で、material 登録前に次の対応を行う。

1. `project://assets/textures/color.png` と物理 path を
   `MaterialContainer::registerReloadableTextureFile` へ渡す。
2. 返った `GlobalTextureId` を `MaterialInfo` の対象 texture slot に設定する。
3. windowed player を起動し、同 path の PNG を別色の PNG で上書きする。
4. `reload: texture project://assets/textures/color.png ok (<n>ms)` を確認し、描画色が
   次 frame から変わることを確認する。shape を変えた場合も logical ID は維持される。

標準の `project init` 雛形は独立画像を material に登録しないため、今回の自動 fixture は
同じ手順を実 FS watcher + 実 Vulkan image readback で自己完結に検証している。

## 境界

- shader poll の撤去、shader/source include handler は HR2-S のまま。
- material values の SSBO update handler は HR1-M のまま。
- model / fragment rebuild は HR2-G のまま。
- `.surface` や material values の既存 loader/register API は変更していない。
