# WP171 負債 LIFETIME0 — exceptional teardown 完了レポート

日付: 2026-07-18
対象: `agent/wp171-lifetime0`
判定: **完了**

## 1. 結論

起動途中の失敗、実行中 fatal、game-logic reload の失敗で共用していた runtime
teardown を、明示した規範順で各工程を個別に保護する実装へ変更した。terminal shutdown
では最初に module 生成を閉じ、GPU idle、owner callback、physics、ECS、model instance、
behavior deferred mutation、pending/frozen event、Vulkan deletion queue の順で drain する。
一工程が例外を投げても後続工程を継続する。

game-logic reload は同じ drain 順を使うが terminal shutdown には移行せず、DeletionQueue
を閉じない `runtime_reset` とした。これにより reload 後も module graph と GPU deferred
release を再利用できる。

deferred GPU callback が raw owner を使う直前に weak token だけを確認していた競合は、
callback lease に置き換えた。owner destructor は新規 lease を閉じ、実行中 callback の
完了を待つ。event payload と behavior deferred mutation は DLL unload より前の明示工程で
破棄する。generic topological container は導入していない。

## 2. 調査時点の現状図

```text
PelicanCore::run() の catch / 正常終了
        │
        └─ RuntimeTeardownGuard
             waitIdle
               → behavior deactivateAll（deferred mutation も暗黙 clear）
               → physics clear
               → ECS clear
               → model instance clear
        │
        ├─ shutdownConfiguredGameLogic() / DLL unload
        └─ FastModuleContainer の逆生成順 destructor

明示順に含まれていなかった寿命:
  static event registerer ─ pending_events / deliver_now_events(frozen)
  BehaviorAttachmentArena ─ deferred_mutations
  DeletionQueue           ─ frame 遅延 GPU resource / callback
  VertBufContainer        ─ weak token 確認 → raw this 使用
  MaterialContainer       ─ weak token 確認 → raw this 使用
```

`FastModuleContainer` が記録するのは constructor 中の module dependency であり、static
event queue、フレームを越える deletion callback、DLL-defined payload destructor は graph
edge ではなかった。逆生成順だけでは、これらを owner unload より前に確実に破棄できない。
また weak token の `expired()` と raw pointer 使用の間には owner destructor が入れるため、
module の逆順を固定しても callback 実行との競合は閉じない。

## 3. 実装後の規範

terminal shutdown は次の一方向の順序を正とする。

```text
beginShutdown（新規 module 生成を fail-fast）
  → wait-idle
  → owner-callbacks
  → physics
  → ecs
  → model-instances
  → deferred-mutations
  → pending-events（pending + frozen）
  → deletion-queue（close + flush）
  → game-logic registration cleanup / DLL unload
  → module destructor（既存の逆生成順）
```

| 順 | 規範 step | 所有権上の目的 | 未初期化時 |
|---:|---|---|---|
| 0 | `beginShutdown` | unwind 中の遅い module 生成を拒否 | phase のみ閉じる |
| 1 | `wait-idle` | GPU 使用中 resource を解放対象にしない | no-op |
| 2 | `owner-callbacks` | behavior instance の `onDestroy` を owner/DLL 生存中に完了 | no-op |
| 3 | `physics` | physics 側参照を ECS より先に切る | no-op |
| 4 | `ecs` | entity/component と付随 callback を破棄 | no-op |
| 5 | `model-instances` | model instance の GPU resource 返却を発行 | no-op |
| 6 | `deferred-mutations` | callback 中に積まれた behavior mutation を明示破棄 | no-op |
| 7 | `pending-events` | pending/frozen の DLL-defined payload を unload 前に破棄 | static queue を drain |
| 8 | `deletion-queue` | deferred GPU callback を owner/module 破棄前に完了し、遅い enqueue を拒否 | no-op |

全 step は `cleanupStep` で独立に捕捉する。startup 途中で module が未生成ならその step は
no-op とし、生成済みの queue だけを同じ順で drain する。DeletionQueue は terminal drain
開始後の `defer()` / `beginFrame()` と drain callback からの再入 enqueue を名前付き
`logic_error` で拒否する。

`runtime_reset` は step 1〜8 の順を共有するが `beginShutdown` を行わない。最後は
DeletionQueue の `flushAll()` だけを行い、queue を再利用可能に保つ。この区別は
game-logic reload の既存契約に必要である。

## 4. owner callback の寿命

`DeferredCallbackLifetime` は mutex 下で callback lease 数と受付状態を管理する。
VertBuf/Material の deferred callback は raw owner に触る前に lease を取得する。

- owner destructor の `closeAndWait()` は新規 lease を拒否する。
- 取得済み lease がある場合は callback が返るまで owner destructor を待たせる。
- queue に残っていて未実行の callback は後から lease を取得できず、owner を参照しない。
- state の検査と active count 増加を同じ lock 内で行い、旧 weak-token の check/use race を
  閉じる。

event と behavior の queue は要素をlocal vectorへ swapし、そのlocalを規範step内で
破棄する。DLL-defined deleter/destructor が unload 後へ持ち越されない。

## 5. generic topological container を導入しなかった理由

今回の暗黙 edge は module constructor dependency ではなく、「queue を閉じる phase」、
「in-flight callback lease」、「static queue 内 payload」の三種である。module destructor の
topological sortだけでは callback の実行中状態やqueue受付停止を表現できない。

対象 queue は event、behavior mutation、DeletionQueue の三つに限定して列挙でき、
owner callbackを含む規範順とfail-fastをfixtureで直接固定できた。そのため既存の
`FastModuleContainer` の constructor dependency / 逆生成順は維持し、汎用DAGの追加は
過剰と判断した。
