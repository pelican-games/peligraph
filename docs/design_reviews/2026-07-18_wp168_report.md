# WP168 SNAPSHOT0 実装報告

日付: 2026-07-18
対象ブランチ: `agent/wp168-snapshot0`

## 1. 結論

`ImportSceneSnapshotRequestV1` を受ける `import_scene_snapshot` RPC を実装した。
engine は version、64 MiB、SHA-256、parse/semantic、current scene の順で検証し、
全検証が成功した後だけ snapshot bytes を `ProjectBasicConfig` の in-memory scene
source として公開して current scene を reload する。通常 project の scene file は
書き換えない。

import document は scratch session の次の `AuthoringObjectId` から全 object を再採番する。
source session の ID は移植しない。loader または fault injection が失敗した場合は、
allocation-free swap で旧 document と revision/ID allocation authority を復元する。

schema evolution と export/import compatibility の acceptance owner は本 WP とした。
WP154 の export schema と `ImportSceneSnapshotRequestV1` の field/意味は変更せず、
export→import→export の byte/digest/semantic 等価 fixture で一組として固定した。

## 2. 検証 5 段と fixture

| 順序 | gate / stable code | 実装 | fixture |
|---|---|---|---|
| 1 | `schema_version == 1` / `unsupported_snapshot_version` | adapter と typed service の先頭で検査する。unsupported request は payload/未知 field を調べない。 | `ImportSceneSnapshot V1 enforces five ordered gates without publication`: version 2 と oversized payload の組合せでも version error。 |
| 2 | UTF-8 bytes ≤ 64 MiB / `snapshot_too_large` | `semantic_scene_bytes.size()` を digest より前に検査する。 | 同 fixture: 64 MiB + 1 byte と不正 digest の組合せでも size error。adapter でも後続 required field 欠落より size を優先。 |
| 3 | DigestV1 SHA-256 一致 / `digest_mismatch` | algorithm が `sha256` であり、小文字 hex が実 bytes の再計算値と完全一致することを検査する。 | 同 fixture: 64桁の不一致 digest。publication callback 0 回。 |
| 4 | parse + semantic validate / `snapshot_invalid{detail}` | `AuthoringSceneDocument::load` で JSON parse と `pelican.scene` v1 semantic validation を行う。例外本文は RPC `data.detail` に格納する。 | 同 fixtureの壊れた JSON、`import_scene_snapshot_v1.json` の設計書厳密 JSON 例。例の placeholder digest は fixture 内で実 bytes から再計算し、digest gate の次の semantic gate へ到達する。 |
| 5 | `current_scene_id` 存在 / `scene_not_found` | validated document の全 scene key から検索する。 | 同 fixture: semantic-valid bytes + `absent`。publication callback 0 回。 |

各負例の後に target の semantic bytes、cache address、`SceneRevision` を検査した。
5 段を通過した後の dependency fault も `snapshot_invalid{detail}` となり、同じ不変条件を
維持する。RPC error data は既存の `code` に加え、`snapshot_invalid` のときだけ
`detail` を持つ。

## 3. 公開 transaction と fault

```text
ImportSceneSnapshotRequestV1
        |
        v
version -> size -> digest -> parse/semantic -> current scene
        |
        v
fresh AuthoringObjectId で unpublished document を全構築
        |
        v
ProjectBasicConfig の prepared document swap
        |
        v
SceneLoader current scene reload + runtime binding 再収集
        |
        v
success response {status:"imported", scene_revision, current_scene_id}
```

`ProjectBasicConfig::publishPreparedSceneDocument()` は SAVE0 と import が共有する
allocation/decode/I/O-free の cache 公開経路である。import は disk baseline digest と
scene file に触れない。`AfterCandidatePrepare`、`AfterPublication`、loader callback throw
を fault fixture に置き、全てで旧 cache address、旧 revision、旧 semantic bytes、disk
bytes を確認した。成功時だけ revision が一度進み、全 object ID が旧 session の最大値より
大きくなる。

## 4. round-trip fixture

CPU fixture `multi_scene_roundtrip.json` は次を含む。

- `main` と非 current の `secondary`
- collider/light と codec 未登録の `unknown_read_only`
- envelope/scene/object 独自 metadata
- integer/float/null と nested array の宣言順

WP154 export bytes を target session へ import し、再 export の
`semantic_scene_bytes` byte 完全一致、SHA-256 完全一致、raw JSON semantic equality、
非 current scene equality を確認した。source ID は 1 から、target ID は 1000 から始まり、
identity が移植されないことも固定した。

実 player の E2E は同時に起動した human/scratch の別 process で次の sequence を実行した。

```text
human PID 91904: export_scene_snapshot
  scene_revision=1, current_scene_id=default_scene
  bytes=403
  digest=a9cd998ab6ef6142fa9787bdd929119d7f6831e9f53f530d1eb9aea79f61e932
scratch PID 71244: import_scene_snapshot
  scene_revision=3, status=imported
  source AuthoringObjectId=1 -> scratch AuthoringObjectId=8
scratch: scene_tree -> export_scene_snapshot -> step_frame
  bytes/digest/current_scene_id equal, disk_unchanged=true
両 process: context 終了後の残留 0
```

E2E bytes は複数 scene、非 current scene の unknown raw component、`-0.0`/指数表現を
含む raw numeric array、非ソート array order を含む。human/scratch は同じ project root を
read-only 共有する。scratch だけが事前 import で 5 object の別 identity range を消費し、
本 import 後の最初の ID が 8 であることにより再採番を実 process でも証明した。

## 5. helper と公式スイープ手順

`tools/pelican_rpc.py` に `import_scene_snapshot(payload)` を追加した。既存
`export_scene_snapshot(payload)` と同じ素通し helper であり、client-side validation や
第二 serializer は持たない。

`docs/manual/10_tools.md` の RPC 章に次の公式 sequence を追加した。

1. human session で `allow_pending=false` の export を行い revision R を保持する。
2. 通常 project root を共有する scratch process を起動し、required 4 fields だけを import する。
3. scratch 内で overrides sweep、`eval_preview` / `render_preview`、必要な capture を行う。
4. 採用値だけを human session へ `base_revision=R` の通常 edit 一件で送る。
5. `stale_revision` なら自動再送せず、現在値を query/re-export して人が再判断する。
