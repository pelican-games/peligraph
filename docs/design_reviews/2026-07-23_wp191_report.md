# WP191 完了レポート — physical target planner runtime integration

日付: 2026-07-23

## 結果

WP189 の data-only `VulkanTargetPlan` と WP190 の実行用 MSAA bridge を
単一の lowering 経路へ統合した。runtime は pass JSON から attachment graph を
再構築しない。現在の経路は次のとおりである。

```text
normalized config
  -> FrameGraphDefinition
  -> CompiledLogicalRenderGraph(shadow adapter)
  -> VulkanTargetPlan
       - physical format / representation
       - attachment-connected sample-count plan
       - per-resource resolve requirement
       - per-scope rasterization sample count
  -> RenderTargetDefinition / CompiledFrameGraphExecution
  -> Vulkan executor
```

`CompiledFrameGraphExecution` は `VulkanTargetPlan` を所有し、従来の
`ResolvedSampleCountPlan` view はその immutable plan への alias とした。
`currentFramePlanJson()` も同じ physical plan を `physical_target_plan` として
公開するため、診断 dump と実行時 resource contract が分岐しない。

## 実装した契約

### project planner

- `VulkanSampleCountPlanRequest` を `VulkanTargetPlanRequest` に追加した。
- logical render node の image output から attachment connected component を導出する。
- geometry scope は core の pass-type JSON を再解釈せず、adapter が付けた
  `raster_geometry` node label を入力にする。
- `VulkanPhysicalResourcePlan` が `rasterization_samples` と
  `resolve_required` を持つ。
- `VulkanPhysicalScopePlan` が `rasterization_samples` を持つ。
- sample 数または resolve contract が異なる resource は alias しない。
- sample 数が異なる render node は tile rendering scope に fuse しない。
- 任意名の追加 G-buffer attachment も同じ component/capability 解決へ入る。

### current Vulkan runtime adapter

- `FrameGraphDefinition` の target を depth、external swapchain、または
  `pelican.render.legacy_opaque_image@1` として logical shadow graph へ型付けする。
  任意の data G-buffer を color signal と偽らない。
- 実 physical device の `maxColorAttachments`、format sample counts、
  depth resolve availability を target facts/capabilities に変換する。
- 現 runtime が消費できる topology は materialized image のみを advertise する。
  tile-local / transient / alias plan を誤って実行しない。
- physical plan の format/representation を既存 `RenderTargetDefinition` と照合し、
  sample 数だけを plan から適用する。
- swapchain は external かつ 1x でなければ登録を拒否する。
- 複数 frame graph が同じ attachment に異なる physical sample 数を要求した場合は、
  silent overwrite せず登録を拒否する。

## 削除した重複

旧 `renderingsamplecount.cpp` にあった次の runtime-only 実装を削除した。

- normalized JSON の `rendering_passes` 再走査
- pass type string による geometry 判定
- runtime 固有 disjoint-set と attachment group 構築
- registration boundary に重複していた device sample query

残った core コードは、既存 runtime resource を logical/target planner の入力へ写し、
返った physical contract を検証・適用する adapter である。

## 意図的な残件

今回 runtime が consume するのは current executor と一致する
`materialized_image` contract である。WP189 の tile-local/transient/alias 候補は
引き続き pure planner で検証できるが、Vulkan native rendering scope の生成と
resource allocator への接続は未実装である。

次も本 WP には含めない。

- XR swapchain の MSAA / multiview lowering
- material fragment-output の固定 5-MRT ABI 可変化
- compute/CPU task と buffer を含む execution linker
- physical plan eject / direct authoring
- cross-graph attachment contract の自動統合

次段は RPE9 の `GraphVariantPolicy` と XR/preview variant 境界を優先し、
その後に tile-native scope または material output schema を独立 WP として扱う。
