# WP105 完了レポート — アセット HR1-M material values 差し替え

## 結論

`.material.json` を watcher の `AssetKey` から WP98 の transaction group へ接続し、
再 parse と WP76 binder/lowering を実行した後、同一 std140 layout の custom values だけを
既存 `MaterialBuffer` SSBO へ書き戻す HR1-M handler を実装した。

成功時も `GlobalMaterialId`、descriptor set、descriptor revision、pipeline は変化しない。
壊れた JSON、型不一致、宣言範囲外、material の欠落、surface/layout 変更、`values` 以外の
変更は candidate を破棄し、旧 SSBO 値を維持して `last_reload_error` と名前入り WARN を残す。

## 実装面

### MaterialContainer の update API

- `MaterialInfo` と内部 material record に `Std140Layout` と custom values の CPU mirror を保持する。
- `updateMaterialValues(GlobalMaterialId, Std140Layout, span<byte>)` は layout の member 名、型、
  offset、size、alignment を完全一致で検証し、該当 material の
  `MaterialGpuData::custom_values` 範囲だけを更新する。
- bytes-only overload も現在の登録済み layout を必須条件として同じ経路へ委譲する。
- 既存 `registerMaterial()` の ID 発行、descriptor/pipeline 作成、texture reverse index の挙動は
  変更していない。reload は明示 opt-in の `registerReloadableMaterialValuesFile()` だけで有効になる。

### HR1-M handler

- 一つの material document に複数の `{material name, GlobalMaterialId}` binding を登録でき、
  各 material は `material-values` logical table の独立 resource になる。
- document parse actor、surface compatibility fake actor、material values actor を同じ WP98 group に
  登録する。values actor は document と fake surface actor の後に commit される。
- logical resource の source/reverse dependency は material document `AssetKey` と surface key を使う。
  1000 reload 中も logical ID、resource count、live bytes は不変だった。
- registry publish 後の retire sink で SSBO を更新するため、candidate の parse/validate/stage が
  失敗した場合は live SSBO に触れない。

## HR-C4-3 境界

本 WP は same-layout values update と surface compatibility の fake actor までに限定した。
実 `.surface` の再 parse、shader/pipeline candidate、`.surface + .material.json` の cross-file atomic
transaction は実装していない。surface reference または layout の変化を検出した場合は、
material 名と `HR2-S transaction required` を含む WARN を出して旧値を継続する。

shader の既存時刻 poll、surface handler、model/fragment handler、ECS は変更していない。

## fixture

`materialvaluesreload_test` で次を固定した。

1. WP76 の 64-byte std140 layout fixture を再利用し、実ファイルの値変更を再 parse/lower する。
2. SSBO readback capture が `4.0 -> 12.0` に変化する一方、同じ document のもう一つの material は
   `9.0` のままであること。
3. `GlobalMaterialId`、pipeline layout、descriptor revision が変化しないこと。
4. broken JSON、float への文字列指定、min/max 範囲外、surface/layout drift で旧 SSBO capture を
   維持し、`last_reload_error` に material 名が入ること。
5. 同一 asset 1000 reload で logical resource ID、resource count、live bytes が不変であること。
6. 実 filesystem watcher の gate が replay 理由で閉じている間は変更が発火せず、再開 barrier 後の
   次の変更だけが反映されること。

## 所要時間

この環境の focused run では、same-layout の parse/lower + transaction publish + SSBO update は
**1 ms**、reject candidate は **0–5 ms** だった。1000 reload fixture では定常時のログは概ね
**1 ms/reload** だった。
