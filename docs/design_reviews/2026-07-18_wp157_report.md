# WP157 E-RPC1a 着手前 blocker レポート

日付: 2026-07-18
対象: 編集 rpc + JOURNAL0（E-RPC1 第一分割）

## 1. 結論

WP157 の実装には着手していない。正本が要求する通常 edit 6 op を、変更禁止の
`EditorProjectionTransaction` 経由かつ document/runtime failure-atomic に実行するための
先行 API が揃っていないためである。

ゴール文書は「`editorprojectiontransaction.{hpp,cpp}` は消費のみ（変更禁止 — 不足が
あればレポートに質問）」および「逸脱・不明点があれば実装せずレポートに質問を書いて
終了」と明記している。set/reparent だけの部分実装、document だけを更新する実装、または
既存 one-shot runtime mutation を transaction の prepare 中に呼ぶ実装は、いずれも
§1-2 の全 command preflight、failure atomicity、committed transaction だけを journal に
記録する条件に反する。そのため source / fixture / golden は変更していない。

## 2. blocker の機械的根拠

### 2.1 spawn / destroy を staged document にできない

`EditorProjectionTransaction::commit()` は command 列を複製 JSON に適用した後、必ず
`AuthoringSceneDocument::stage()` を呼ぶ
（`src/core/loader/editorprojectiontransaction.cpp:670-681`）。一方、現行 `stage()` は
次を明示的に reject する。

- scene の追加・削除
- object 数の変化
- object の追加・削除・rename・reorder

該当箇所は `src/core/loader/authoringscenedocument.cpp:107-147`、特に
`projection transaction cannot add, remove, or reorder authoring objects` である。
従って generic `EditorProjectionCommand::apply` で JSON に spawn/destroy を記述しても、
transaction の stage で必ず rejected となる。現行 metadata API には、新 object へ
session-stable `AuthoringObjectId` を割り当て、destroy closure の生存 object ID を保持し、
inverse spawn で同じ authoring identity を再 bind する公開操作もない。

### 2.2 add / remove_component を aggregate transaction に参加させられない

WP152 の公開面 `ECSArchetypeMigration::add/remove` は、prepare token を caller に返さない
one-shot API である（`src/core/ecs/archetypemigration.hpp:50-64`）。呼出し内部で prepare と
publication を完了するため、これを `EditorProjectionAdapter::prepare()` から呼ぶと live ECS
を document publish 前に変更し、後続 adapter fault 時に aggregate rollback できない。

逆に `EditorProjectionAdapter::publish()` から呼ぶこともできない。publish は `noexcept` が
契約であるのに対し、migration の construct / populate / init / adapter prepare は throw
し得るからである。`EditorProjectionCallbackAdapter` は callback の型を提供するだけで、
ECS migration の unpublished state または inverse token を所有しない。

### 2.3 spawn / destroy の runtime prepared adapter がない

現行 transaction の concrete runtime participant は
`TransformProjectionAdapter` だけである。renderer/model、camera、ECS archetype、light、
phys、behavior 用の `EditorProjectionCallbackAdapter` は typed junction だが、caller が
prepare/publish/rollback/finish の実体と state を提供しなければならない
（`src/core/loader/editorprojectiontransaction.hpp:174-204`）。

現行 `SceneLoader::load()` / object create / remove 経路は ECS、renderer、camera、light、
phys、binding を live に構築・破棄する通常ロードであり、WP157 が消費できる
「全 prepare 済み・publish noexcept・rollback noexcept」の spawn/destroy token を公開して
いない。従って destroy closure の lossless inverse を journal に保存できても、その runtime
closure を aggregate transaction の publication 区間で安全に unpublish/rebind できない。

### 2.4 set_component_value の全 codec に対応する aggregate adapter がない

`makeSetComponentValueCommand()` は staged authoring component の decode/canonical encode
までは行える。transform は `TransformProjectionAdapter` へ接続できる。しかし camera、
light、collider、simplemodelview 等について、現行 `ComponentCodec::runtime_apply` は direct
target への apply であり、transaction が要求する prepared state と完全 inverse token を
構成する production owner が公開されていない。従って通常 edit を transform だけに限定
すると、E-C4 の set_component_value 行全体を満たさない。

### 2.5 指定 commit 点の hook がない

正本の commit 点は runtime reload 後・`freeze_events` 前の一点である。現行
`updateFrameState()` は reload publication の直後にそのまま `freeze_events` へ入り
（`src/core/appflow/framephase.cpp:90-100`）、windowed RPC dispatch は
`updateFrameState()` の終了後に行われる（`src/core/appflow/loop.cpp:455-459`）。

Editor edit queue を正しい一点で実行する callback/hook は公開されていない。これは上の
projection blocker が解消すれば小さく追加できるが、現状のまま RPC handler 内で commit
すると指定 boundary と acceptance/execution 二段を満たさない。

## 4. 確認したい質問

1. WP157 より前に、`AuthoringSceneDocument` の structural stage API（object insert/remove、
   stable `AuthoringObjectId` allocation/rebind、declaration interval の保持）を追加する補完 WP
   を置くか。それとも WP157 に同ファイルの変更を明示的に許可するか。
2. WP152/E-PROJTX0 の補完として、ECS add/remove と object spawn/destroy の
   **prepare-only token**（publish/rollback は `noexcept`）を公開する補完 WP を置くか。
   現行 one-shot `ECSArchetypeMigration::add/remove` を aggregate prepare 中に呼ぶことは不可で
   ある。
3. camera/light/collider/model を含む全 registered codec について、production の
   `EditorProjectionAdapter` 構築 owner はどの WP/file とするか。WP157 が新 adapter を所有
   する場合、変更可能領域と必要な prepared API を明記してほしい。
4. runtime reload 後・`freeze_events` 前へ editor commit を差し込むため、
   `framephase` / interactive loop の小さな hook 追加を WP157 の変更範囲として許可するか。

推奨する着手順は、(1) structural authoring stage、(2) ECS/object/special adapter の
prepared token、(3) frame-boundary hook を E-PROJTX0 補完として先に固定し、その後に
WP157 の ticket/CAS/ActorId/gate/journal/RPC fixture を一括実装する順である。

## 5. 未実施 gate と WP158 持ち越し

実装を開始していないため、WP157 focused fixture、全 CTest、golden、player 8 秒は
完了判定として実施していない。既存 test/golden byte は変更していない。

undo/redo RPC、ticket preview lease、can_preview 実体、forced-abort、E-C3-2 の
reload/scene transition/callback 競合 fixture は、正本どおり WP158 持ち越しのままである。
