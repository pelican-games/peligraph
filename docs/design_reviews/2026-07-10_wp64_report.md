# WP64 実装レポート — legacy 実行系の撤去

実施日: 2026-07-10

対象: `agent/wp64-legacy-removal` (base `0ef2e69`)

環境: Windows 10.0.26200 / MSVC 19.44 / Vulkan SDK 1.4.309 / NVIDIA GeForce RTX 5080 (driver 32.0.15.9186)

## 結論

pure-render を legacy に落としていた `has_compute` gate と
`executeLegacyRenderingPasses` を撤去し、全 rendering config を
`FramePlan` の順序で実行するようにした。撤去前 A/B では既存 Renderer
golden 13 件の trace と RGBA が完全一致した。既存 golden 16 件を維持し、
明示 edge の実行順を画像で固定する 1 件を追加したため、最終 golden は
17 件である。

## 撤去前 A/B ゲート

A/B 計装だけを先行コミット `c207fec` に固定してから撤去した。

- A: 撤去前の自動選択。pure-render は legacy、`compute_buffer` は従来どおり planned
- B: 全 config を planned に強制
- 対象: 既存 golden 16 件のうち Renderer を通る全 13 件
- 比較: node 名・種別・実行順、color/depth の load/store/clear、入力と attachment の実行後 layout、frame target の最終 layout、最終 RGBA byte 列
- 結果: 13/13 で trace 完全一致、RGBA byte 列完全一致。意味論差分の発見なし

`clear`、`fullscreen`、`triangle` の 3 件は監査記載どおりテスト自身が
command buffer を記録し Renderer を通らないため、画像回帰だけを維持した。
最終状態では A/B selector を削除し、既存 13 件と新規 1 件の採取済み trace を
`test/fixtures/renderer_execution_traces.json` と比較する。

## planned 固有意味論と実行列

`explicit_order` golden を追加した。宣言順は
`red_after_blue`, `blue_first` だが、`red_after_blue.after = [blue_first]` により
実行 trace は `blue_first`, `red_after_blue` となる。最終画像が赤になることまで
固定しており、旧 legacy の宣言順実行なら青になって失敗する。

全 Renderer trace test は実行された node 名列を
`framePlanOrder(plan)` と直接比較する。GPU timing 有効の `explicit_order` では、
timing の node 名・順序も同じ列で、query 数が `2 × node 数` であることを確認する。

## validation / synchronization validation

Debug の Khronos validation layer に
`VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT` を明示的に追加した。

`compute_buffer_headless_player` を次の chain に拡張し、in-flight 2 を超える
5 frame を device `waitIdle` なしで実行した。

1. material render → compute (`seed_image`、image)
2. compute → fullscreen render (`result_image`、image)
3. fullscreen render → compute (`sampled_color`、image)
4. compute → compute (`raw_color`、buffer)
5. compute → fullscreen render (`compute_color`、buffer)

offscreen target 自身の frame fence 待ちは通常の再利用同期として残るが、frame 間の
device `waitIdle` はない。終了時だけ既存 Loop の wait/flush を行う。結果は exit 0、
`Validation Error` / `VUID-` とも 0 件だった。

### synchronization validation が発見した既存 hazard

最初の実 swapchain smoke で planned/legacy 差分ではない既存同期不足を検出した。

- `LOAD` attachment の read access が color/depth layout barrier の access mask に無く、`SYNC-HAZARD-READ-AFTER-WRITE`
- acquire semaphore の wait stage より前に swapchain layout transition が実行可能で、`SYNC-HAZARD-WRITE-AFTER-READ`

color/depth attachment barrier を read|write access にし、swapchain acquire wait を
top-of-pipe へ広げて修正した。修正後の実ウィンドウ 5 秒 smoke は swapchain の
acquire/present を継続し validation marker 0。プロセスは smoke 後に停止した。
実ウィンドウの自動 resize 操作は行わず、resize 時の resource 再生成と rebind は
次節の deterministic test で検証した。

## resize / shader hot reload rebind

fullscreen descriptor が保持する実 `vk::ImageView` と binding revision をテストで観測した。

- shader source の timestamp を更新して次 frame を実行し、pipeline rebuild 後に revision が増加すること
- hot reload だけでは bound image view が変わらないこと
- render target を再生成し、旧 view と新 view が異なること
- rebind 後の descriptor が新 view を保持し、次 frame が validation error なしで完了すること

すべて PASS。production の resize/hot-reload 呼出位置は変更していない。

## barrier コンパイルと性能

撤去前 planned executor は毎 frame `unordered_map` と `unordered_set` を構築し、
各 node から全 barrier を走査していた。登録時に barrier の source index/kind と
target node 別 incoming list をコンパイルする形へ変更した。

- executor 所有の frame-local dynamic container site: 2 → 0
- barrier 走査: O(V×B) → O(B) (各 target node の incoming barrier のみ)
- trace JSON: テストで明示有効にした場合だけ生成。通常実行は allocation なし

Release の空 scene + example 代表 pass config、160×90、200 frames を warm-up 後に
3 process 実行した。値は process 起動・終了を含む wall-clock / 200 である。

| 経路 | run 1 | run 2 | run 3 | 中央値 |
|---|---:|---:|---:|---:|
| 撤去前 legacy (`c207fec`) | 13.8125 ms | 14.0774 ms | 13.9706 ms | 13.9706 ms |
| planned-only + barrier compile | 14.6708 ms | 14.5344 ms | 14.7159 ms | 14.6708 ms |

中央値差は +5.0% で、監査の 10% budget 内。専用 allocator hook と in-process
per-frame percentile recorder はないため、正確な allocation call 数と CPU p95 は
この計測では取得していない。代わりに executor 内の動的 container site と走査量を
上記のとおり構造的に固定し、同一条件の process-level 中央値を回帰基準とした。
