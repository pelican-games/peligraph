# WP195 完了レポート — GPU owner-scope replacement and generation lease

日付: 2026-07-24

## 結果

同じ owner scope の render config を、旧 frame が参照中でも原子的に置換できるようにした。
新 generation は同名 target / buffer / compute task に新しい単調増加 handle を割り当て、
旧 generation は compile 時に固定した typed handle と resource lease から旧 resource を
参照し続ける。最後の generation lease が消えると旧 registry membership を exact handle で
退役させ、Vulkan payload は既存の遅延破棄経路へ渡す。

```text
active generation N
  owner scope S -> old registry handles + old scope lease
  frame A ------^

prepare replacement S
  hide only S's current-name facade
  checkpoint all registries
  register same names as fresh monotonic handles
  compile frame graph with generation-local typed bindings
  build candidate N+1 + new unarmed scope lease

publish
  failure -> rollback names and fresh memberships; N remains active
  success -> CAS N+1, arm new lease

retire
  frame A releases N
  last old lease releases exact old memberships
  Vulkan payload enters the existing DeletionQueue
```

## scope-aware replacement

`RenderPipelineGpuRegistrationArena` は active GPU arena から置換対象 owner scope を受け取る。
prepare 開始時に旧 target / buffer / compute task の名前だけを current facade から隠すため、
同名登録は新規 handle として成立する。一方、旧 ID の live record は削除せず、旧 generation
からの typed access を維持する。

同じ owner の runtime program は candidate から一度除去してから再構築する。同名 program は
既存 `RenderingPassId` と安定した公開順を再利用し、候補に存在しない program は新 generation
から消える。別 owner が同じ program 名を上書きする操作は拒否する。

flat / XR 等の owner 間に暗黙の resource 依存が残っているため、置換されない別 owner program
には旧 scope lease を保守的に継承する。その program 自身が後で置換されれば継承 lease は
外れる。これは依存を推測して早期解放するより安全側の暫定規則であり、将来は program-to-scope
dependency を manifest に明示する。

## generation-local resource binding

`CompiledFrameGraphExecution` は次の immutable binding を所有する。

- render-target name → `GlobalRenderTargetId`
- frame-graph buffer name → `FrameGraphBufferId`

renderer の barrier、snapshot copy、output transform、paired sRGB、final layout、XR mirror
intermediate はこの snapshot を使う。compute task と fullscreen descriptor も登録時に
target / buffer ID を解決して保持し、実行中に mutable name table を引き直さない。
`XrMirrorSink` は generation replacement 後の source ID を使用直前に再bindする。

これにより、同じ名前が新 scope に差し替わっても旧/new generation が異なる handle を同時に
正しく参照できる。

## generation-owned registry lease

scope manifest は内部 `ScopeRegistrationLease` を一つ保持する。lease は candidate prepare
中は unarmed で、runtime root の CAS 成功後だけ arm される。未公開 candidate の破棄や
明示 rollback が active resource を retire することはない。

arm 済み lease の最後の参照が消えると、次の順で登録 membership を退役させる。

1. fullscreen / debug / debug-text / shadow / velocity pass
2. compute task
3. frame-graph buffer / render target
4. graphics / compute pipeline
5. shader bundle

全 registry handle は退役後も再利用しない。これにより、古い typed handle が偶然別 resource
を指す ABA を防ぐ。共有 descriptor-set-layout cache は scope-owned membership ではなく
engine cache として維持する。

## failure atomicity

WP194 の5段 fault injection を初回登録だけでなく same-owner replacement にも適用した。
runtime prepare 後・publish 前で失敗させた場合に、次を確認した。

- active runtime generation と GPU arena scope は旧値のまま
- target / buffer / compute task の current name binding は旧 ID へ戻る
- 全対象 registry の membership count と旧 handle の metadata は不変
- candidate の新規 handle は live table に残らない
- fault 後の retry で replacement を正常公開できる

## RPE10b3 へ残す境界

WP195 は registry membership の所有者を runtime generation に結び付けたが、submission
完了そのものを generation lease に結び付けてはいない。現在の Vulkan payload は既存
`DeletionQueue` の論理 epoch に委譲される。
また registration は engine owner thread の直列化区間を前提とし、mutable registry の
汎用 concurrent update API にはしていない。

次の WP196 / RPE10b3 では次を接続する。

- submission が参照した runtime generation の fence token
- CPU generation 解放と GPU fence 完了の両方を満たす retire
- FileWatcher / `ReloadGate` の変更 coalesce
- frame boundary での config / shader candidate publication
- reload 失敗時に active generation を維持する end-to-end fixture

ここまで接続して初めて、保存操作から GPU in-flight 安全な pipeline hot reload までが
一つの運用経路として完了する。
