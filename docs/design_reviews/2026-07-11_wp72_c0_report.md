## 設計 v4 §1 と実コードの差分

### 1. [Major] B8→R8 は「格納バイト従来同等」ではない

現行 `gbuffer_albedo` と `lit_color`、bloom 9 RT は `B8G8R8A8_UNORM` である (`projects/example/passes/main_rendering_config.json:4-7,40-43,58-109`)。material pass pipeline ABI も albedo を B8 と固定する (`src/core/renderingpass/materialpassattachments.hpp:8-14`)。設計 v4 §2-3 の決定はこれらを `R8G8B8A8_SRGB` とするため、transfer だけでなく channel order も変わる。

C1a resolver v1 では旧 B8 order を必ず維持し、C1b でも byte/order 変更を「SRGB view による従来同等格納」と一括しないこと。B8G8R8A8_SRGB を使うか、R8 への明示 swizzle/copy と baseline 理由を持つ必要がある。

### 2. [Major] glTF `emissiveFactor` は float のまま流れていない

設計 v4 §1/§2-3 は `baseColorFactor` / `emissiveFactor` を raw linear multiplier として保護する。しかし現コードで float のまま頂点色へ流れるのは、texture がない場合の `baseColorFactor` と `COLOR_0` である (`src/core/model/gltf.cpp:460-476`)。

`emissiveFactor` は `toUnorm8` で `[0,1]` clamp + round され、4×4 の solid `R8G8B8A8_UNORM` texture になる (`src/core/model/gltf.cpp:157-173,188-197`)。したがって 1 超の radiometric emissive は現時点ですでに失われる。`KHR_materials_emissive_strength` の実装参照もリポジトリ内にない。

C1 は単なる view 差し替えでは足りず、emissive texture の SRGB color と emissive factor/strength の linear radiometric multiplier を分離する必要がある。

### 3. [Major] shader-lab の末尾変換が v4 §1 に未記載

以下の embed 済み shader に、通常 lighting の `pow(1/2.2)` 以外の末尾変換がある。

- `shader_lab_gltf_lighting.frag:58-59`: exp curve + `pow(mapped, 0.92)`
- `shader_lab_bloom_composite.frag:16-17`: exp curve + `pow(color, 0.92)`
- `shader_lab_present.frag:12-13`: `pow(color, 0.92)`

これらは現行 project graph から参照されないが、`src/core/resources/CMakeLists.txt:39-46` と `src/core/loader/engineresources.cpp:51-58,128-135` により配布 resource である。`pow(0.92)` を creative look として残すなら tone/display shaping の所有を明示し、暗黙の terminal transfer なら削除して `output_transform` に一本化する必要がある。C0 では intent を推測せず `visual_review` とした。

### 4. [Major] 現行 UI は color-page atlas ではない

設計 v4 §2-3 の「UI atlas(color page) / 白テクセルページ」に対応する runtime 実装はまだない。現行 UI は JSON の image ごとに `R8G8B8A8_UNORM` image/view を作る (`src/core/renderer/uicontainer.cpp:54-74,114-145,173-180`)。vertex color もなく、fragment shader は texture をそのまま返す (`src/core/resources/ui.frag:6-12`)。

C1 では「現 UI image slot を SRGB 化する作業」と「将来 UI atlas/color page」を混同しないこと。manifest は現実装を対象にし、未実装 atlas を既存 resource として数えていない。

### 5. [Major] debug font は R8 ではなく RGBA8

設計 v4 §2-3 は font/debug font を `R8_UNORM` 系 data と記す。現行 debug font PNG は image loader により RGBA8 へ展開され、`debugtext.cpp:54-63,208-216` で `R8G8B8A8_UNORM` image になる。shader は alpha だけを読む (`src/core/resources/debug_text.frag:6,13`)。

transfer 禁止という判断は正しいが、「そのまま R8_UNORM」ではない。RGBA8→R8 へ storage layout を変えるなら coverage 値の analytic equality を検査する必要がある。

### 6. [Major] 設計に挙がる capture consumer の一部は未実装・repo 外

実装済み capture point は `readbackLastFrameRGBA8` / `captureLastFrameToPng`、CLI `--render-out`、RPC `capture` である。名前付き中間 RT snapshot API は `src/projects/test` に存在しない。DCC bridge/capture script もこの worktree に存在せず、`docs/dcc_integration_qa_2026-06-12.md:28-45,258-277` に計画だけがある。

従って C1 で直接変更・テストできる consumer と、外部調整が必要な将来 consumer を分けた。manifest の `consumers` は不存在も機械可読に明示する。

## 追加の確認事項

- scene light color は raw float のまま UBO へ渡る (`src/core/light/lightcontainer.cpp:161-198`)。設計 v4 §2-4 の sRGB-authored decode を導入すると、example scene の非 endpoint 色 (`projects/example/scenes/main.scene.json:887-1221`)はすべて見た目が変わる。
- material texture は binding 0..5 の全 slot が単一 `ImageWrapper.format` view を使う (`src/core/material/materialcontainer.cpp:17-24,80-94,188-223`)。glTF loader も texture index ごとに 1 GPU texture しか作らない (`src/core/model/gltf.cpp:509-523`)。dual-use image 対応は設計どおり必須である。
- windowed surface はこの端末で transfer src/dst 対応だが、capability 判定は device/driver/surface ごとに実行する必要がある。この結果を一般保証として扱ってはならない。
- `test/run_compute_headless.cmake:135-155` は material attachment slot を color/data/storage の混在用途に使う。名前や UNORM だけで color role を自動推定すると壊れるため、role metadata が必要である。
- main graph の HDR feature は設計記載どおり `before:present` anchor 不在で compose 不能 (`src/core/resources/features/hdr.json:12`; main graph の末尾は `FinalBloomComposite` → `ui_pass`, `projects/example/passes/main_rendering_config.json:297-316`)。

## canonical anchor 写像

main graph 18 pass は manifest に個別列挙した。要約は次のとおり。

| 現 pass 群 | canonical 区間 |

| bloom 13 pass | HDR off: post_ldr / HDR on: post_main |

test fixture `dummy_feature` の `after:present` は、常設かつ最後の `output_transform` と両立しない。fixture shader 自体が存在しないため意味を推測できず、manifest では「post_ldr への fixture rewrite 要」とした。negative fixture は migratable graph に数えず、それぞれ collision/missing-anchor の失敗目的を維持する。

## capture consumer 監査

実装済み consumer は次の 4 群だった。

1. C++ 共通 API と PNG writer (`rendertarget.hpp/.cpp`)
2. CLI `--render-out` の単発・連番 (`appflow/loop.cpp`)
3. RPC `capture` と `get_status` (`communication/rpcserver.cpp`)
4. direct readback/golden test と 10 本の `run_*.cmake` capture 利用箇所

RPC 系テストは file existence、non-empty、操作前後の byte 差、または deterministic equality だけを検査し、絶対色を検査しない。設計 v4 の linear 0.5 → 188 known-value test は新規に必要である。`run_rpc_inject_input_headless.cmake` の deterministic byte 比較と golden suite は、一斉再基準化手続きの対象になる。

## C1 への引き渡し条件

1. C1a resolver v1 では B8/R8 channel order、sample count、extent、load/store/clear/blend を旧 graph と同一に固定する。
2. この端末では transfer src/dst capability が揃うが、runtime query、usage 追加、layout/barrier/queue ownership trace を実装する。
3. C1b 前に shader-lab の `pow(0.92)` の所有、emissive factor の runtime 表現、UI atlas の実装範囲、generic RT の role を決定する。
4. manifest の `visual_review` 全項目を三者比較表へ転記し、説明不能差分があれば baseline を更新しない。
5. capture contract 2 の metadata と absolute-color gate を、既存 RPC/CLI consumer 更新と同時に入れる。
