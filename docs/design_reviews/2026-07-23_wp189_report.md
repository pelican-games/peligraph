# WP189 完了レポート — RPE6c1 desktop/tile target planner

## 1. 結論

WP189の受け入れ条件を満たした。WP188のdata-only topology / backend probeを入力に、
immutable canonical logical graphから使い捨て可能な`TargetLoweringGraph`を作り、同じ
`GBuffer -> Lighting -> Forward -> ToneMap`をdesktop materialized planまたはtile-local /
transient planへ純CPUでlowerできる。

現行`FramePlan`、Vulkan executor、GPU object、runtime publicationはこのplanをまだ消費しない。
今回追加した`VulkanTargetPlan`はdata-onlyな物理計画fixtureであり、実行所有権とflat 1xの
描画挙動は変更していない。

## 2. ResourcePatternとG-buffer拡張

`ResourcePattern`はlogical typeでもresource名enumでもなく、次を持つcopy可能なplanning policy
である。

- 適用可能な`LogicalTypePattern`
- 順位付きconcrete format候補とrequired capability
- transient / tile-local / alias / storeの選好
- local-read不成立時のmaterializeまたはreject
- byte概算とprovenance

resourceとのbindingをpattern本体から分離した。同じpatternを任意個のG-buffer attachmentへ
適用でき、plannerは`gbuffer_albedo`等の既知名も枚数も列挙しない。fixtureでは標準相当5枚に
custom attributeを1枚追加し、planner変更なしでdesktop/tile両planへ現れることを固定した。

上限はplanner定数でなくendpointの
`pelican.vulkan.max_color_attachments@1` factから取得する。budget以内の7枚は通り、9枚を
budget 8へlowerすると`pelican.plan.color_attachment_budget_exceeded@1`で理由付き拒否される。
実runtimeのshader output / attachment ABIを増やす処理は後続physical adapterの責務である。

## 3. disposable loweringとdialect legality

`makeTargetLoweringGraph()`はcanonical graphのnode/resource/use/region/provenanceを値として
複製し、resourceごとに最大read footprintとfirst/last useを導出する。compile前後でcanonical
logical graph dumpはbyte不変である。

lowering workspaceは次の完了境界を持つ。

1. `canonical_workspace`: `logical`だけがlegal
2. `target_execution_complete`: `execution.gpu`だけがlegal
3. `vulkan_physical_complete`: `physical.vulkan`だけがlegal

各境界で残存dialectを検査する。selected backend probeが宣言したrequired physical featureの
集合をlowering後のplanが超えると
`pelican.plan.lowering_capability_growth@1`でprovider inconsistencyとして拒否する。

## 4. desktop / tile materialization

target plannerは次の有限候補を同時にprobeし、WP188の固定cost tupleで選ぶ。

- `pelican.vulkan.materialized_plan@1`
- `pelican.vulkan.tile_local_plan@1`

desktop endpointではtile capability不足により前者を選び、G-bufferをmaterialized sampled
imageとする。tile endpointではsame-pixelかつrender内で閉じるG-bufferを
`tile_local_attachment`とし、region tagを越えてGBuffer / Lighting / compatible Forwardを
同一scopeへ融合できる。

`neighborhood` / `arbitrary` / `temporal` read、required/external resource、明示store、
snapshot outputはmaterializeする。refraction fixtureではG-bufferをtile-localのまま維持し、
`opaque_snapshot`をstable sampled imageとしてmaterializeする。

## 5. lifetime / aliasとpurge

node orderからresource lifetimeを導き、representation / formatがcompatibleでlifetimeが
非重複のpairだけをWP188のalias policy入力へ渡す。`no_alias` / `isolate` /
`conservative_debug`は既存policyで候補を狭め、選択pairはpairwise-compatibleなalias groupへ
まとめる。

未使用resourceはphysical planからpurgeする。Image / Bufferだけが`ResourcePattern` bindingを
要求し、semantic Value / ObjectSet等はcompile-time既定patternでGPU resourceを作らない。
CPU / external / video backend、scheduler、runtime taskは追加していない。

## 6. 今回に含めなかったもの

- 実`vk::Image`、dynamic rendering scope、barrier、queue、memory aliasの作成・実行
- sample count / resolve / MSAA graph transform
- XR / preview graph variantとmultiview lowering
- physical planのpublic eject形式、game-DLL pattern/provider ABI、`NativeScope`
- CPU physical scheduler、execution linker、動画backend

次はRPE7で`SampleCountRequest`とtarget capability/fallbackの純粋resolveを追加し、RPE8で
current 1x physical adapterを基準に実Vulkan MSAA / resolveへ接続する。
