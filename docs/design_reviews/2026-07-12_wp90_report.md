# WP90 実装レポート — G2 ゲームロジック DLL ホットリロード

日付: 2026-07-12

ブランチ: `agent/wp90-dll-reload`

## 結果

WP90 の v1（全リセット方式）を実装した。`PELICAN_PROJECT/code` は従来と同じ
`pelican_game_sources(...)` を使いながら、player への静的リンクではなく
`pelican_game_logic.dll` になる。player は元 DLL を直接ロードせず、一意名の
shadow copy をロードするため、実行中も元 DLL と PDB を再ビルド・置換できる。

リロードの順序は次のとおり。

1. 元 DLL と、存在すれば PDB を `.pelican-hot-reload/` へコピーする。
2. 候補コピーを一度ロードし、export された ABI version を検証する。
3. 候補の検証用登録を解除して候補を閉じる。ここまでの失敗では旧 DLL に一切触れない。
4. reload-in-progress を立て、WP62 の `RuntimeTeardownGuard` で runtime を例外安全に teardown する。
5. 旧 DLL 所有の system/event 登録を全解除し、旧 shadow DLL を閉じる。
6. 検証済み候補をロードして再登録し、現在のシーンを全再構築する。
7. 切替またはシーン再構築に失敗した場合は、保存してある旧 shadow DLL を再ロードして
   シーンを再構築する。

オブジェクト単位の状態移送は実装していない。system の static instance と ECS/scene は
DLL 世代ごとに破棄・再構築される。

## 主な実装

- `src/core/gamelogic/gamelogicreload.*`
  - shadow DLL/PDB copy、ABI 検証、ファイル更新 poll、transaction/rollback、状態照会。
  - Windows loader のローカライズ済みエラー文字列を JSON-RPC へ混入させず、
    UTF-8 安全な error code と対象 DLL 名を返す。
- `src/core/userpublic/gamelogic.hpp`, `export.hpp`
  - ABI version 1 と userpublic export/import 境界。
  - player と game DLL は MSVC shared CRT (`/MD[d]`) を共有し、STL 登録データの
    DLL 境界解放を安全にした。
- system/event registerer
  - LoadLibrary 中の thread-local registration owner を各登録へ付与。
  - owner 単位の全解除と counting API。event queue に残った DLL 所有 payload も
    DLL を閉じる前に除去する。
- player/CMake
  - `pelican_game_sources` のソースを SHARED library へ追加。
  - game DLL は player import library の userpublic surface のみを参照し、
    engine static library や module singleton を複製しない。
  - project build では player と同じ出力ディレクトリに `pelican_game_logic.dll` を生成。
  - `--game-logic path.dll` で fixture/開発 DLL を明示できる。
- loop/RPC
  - windowed loop は更新時刻を監視し、F5 でも強制 reload できる。
  - RPC に `reload_game_logic` を追加。
  - reload-in-progress 中の全 RPC は method 名入り application error で拒否する。
  - input replay/golden driver 中の reload は決定性保護のため拒否する。
- `projects/example/code/playercontrol.cpp`
  - 同じ playercontrol ソースを fixture v1（speed 2.5）/v2（speed 5.0）としてビルド可能にした。

## Fixture

`game_logic_dll_reload` は実際の `pelican_player` と
`projects/example/code/playercontrol.cpp` から作った 3 DLL を使用する。

- v1 をロードして RPC `step_frame`、`behavior=v1 speed=2.5` を確認。
- player 実行中に元 DLL を v2 で上書き（Windows DLL lock 回避の直接検査）。
- RPC reload 後に `behavior=v2 speed=5.0`、generation 2、systems 1 を確認。
- 非 PE ファイルを置いて load error と DLL 名を確認。その後の frame でも v2 を確認。
- ABI 999 DLL を置いて version mismatch を確認。その後の frame でも v2 を確認。
- v1 へ戻して generation 3、systems 1 を確認。登録数が世代ごとに増えない。

## 検証

```text
cmake -S . -B build-wp90 -DSKIP_DEVSTUDIO=ON \
  -DPython3_EXECUTABLE=%APPDATA%\uv\python\cpython-3.12.13-windows-x86_64-none\python.exe
```

- configure: PASS（Python 3.12.13 を検出）

- CTest: **284/284 PASS**
  - Windows の developer-mode/symlink 権限がない場合だけ既存 PathResolver symlink case が
    CTest 上 `Skipped` になる。失敗は 0。

- `game_logic_dll_reload`: PASS
- replay reload rejection: PASS
- `git diff --check`: PASS

## 8 秒 player 実演

同じ player/RPC fixture を 8 秒待機付きで実行した。wall time は 9.97 秒、終了後の
`pelican_player` process は 0。完全ログは build artifact
`build-wp90/test_artifacts/game_logic_demo_8s/pelican.log` にある。
