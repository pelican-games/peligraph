# WP62 implementation report

Date: 2026-07-10
Worktree: `agent/wp62-ecs-lifecycle`
Toolchain: Visual Studio 2022 / MSVC 19.44.35228, CMake multi-config Release

## Pre-implementation benchmark baseline

The original benchmark issued one 20,000-40,000 entity allocation against a
chunk whose capacity is 4,096 and did not assert the result, so its timings were
not valid. Before changing the ECS implementation, the benchmark was converted
to a typed POD workload and every allocation was split at
`ECSComponentChunk::CHUNK_CAPACITY`. The workload uses a fixed data sequence,
two warm-up runs, eleven measured runs, and reports median/p95.

Only operations with meaningful behavior in the pre-WP62 implementation were
measured. String/over-aligned lifetime, generation-aware stale lookup, free-list
reuse, and PhysWorld-by-ID have no valid pre-implementation baseline.

| Release workload | Median (ms) | p95 (ms) |
|---|---:|---:|
| create POD 1 | 0.006 | 0.006 |
| create POD 4,096 | 0.190 | 0.210 |
| create POD 4,097 (two bounded batches) | 0.172 | 0.178 |
| create POD 100,000 (bounded batches) | 2.993 | 3.358 |
| relocate POD 2,048 times | 0.033 | 0.033 |
| resolve POD hit 1,000,000 times | 7.175 | 7.210 |
| resolve POD miss 1,000,000 times | 2.335 | 2.341 |

The provisional regression budget compares the final implementation on the
same machine and workload: p95 at most 2.0x for POD creation, 3.0x for POD
relocation, and 2.5x for resolve hit/miss. The one-entity case is diagnostic
only because timer and allocator noise dominate it. Correctness requirements
remain mandatory even if a budget is exceeded; an exceedance must be reported
with its cause rather than hidden by weakening lifecycle rules.

## Implementation findings

- Fixed-capacity aligned allocation is required for correctness as well as
  stable addresses during a transaction. Allocating each component array once
  at chunk construction made construction rollback independent of vector
  reallocation.
- The entity table must be provisional during construction. ID entries receive
  refs with `live=false`; only after every populate and init callback succeeds
  are all entries published. A transaction snapshot restores the ID table,
  free-list ordering, fresh chunks, system caches, and versions on failure.
- `clearEntities` can discard chunks while retaining the ID table. Advancing
  generations in ascending index order before later LIFO reuse preserves both
  scene-switch ABA protection and deterministic allocation.
- SceneLoader and PhysWorld could retain WP47's immediate visibility without a
  transform cache: both now retain IDs and resolve the Transform component at
  use time. RPC pending transforms retain the ID observed at parse time and
  verify the same ID again at flush time, so name rebinding cannot redirect a
  queued edit.
- Teardown had to move the module container outside the exception-catching
  scope. A no-throw, idempotent scope guard now clears physics/ECS/model
  instances before reverse module destruction on normal, initial-load failure,
  and loop/RPC exceptions.

### Final Release benchmark

The final benchmark keeps the same fixed workload and adds the cases that only
become valid after WP62.

| Release workload | Median (ms) | p95 (ms) |
|---|---:|---:|
| create POD 1 | 0.006 | 0.008 |
| create POD 4,096 | 0.216 | 0.222 |
| create POD 4,097 | 0.221 | 0.225 |
| create POD 100,000 | 4.193 | 4.656 |
| create string 4,096 | 0.280 | 0.289 |
| create over-aligned 4,096 | 0.157 | 0.160 |
| create string 100,000 | 6.498 | 6.628 |
| create over-aligned 100,000 | 4.990 | 5.456 |
| relocate POD 2,048 times | 0.043 | 0.047 |
| relocate string 2,048 times | 0.047 | 0.050 |
| create from mixed free-list 2,048 | 0.082 | 0.087 |
| resolve POD hit 1,000,000 times | 8.463 | 8.652 |
| resolve POD miss 1,000,000 times | 2.208 | 2.281 |
| PhysWorld query, 512 colliders x 200 | 21.655 | 23.250 |

Against the valid pre-WP62 cases, POD creation at 100,000 is 1.39x p95,
relocate is 1.42x, resolve hit is 1.20x, and resolve miss is 0.97x. All are
inside the provisional regression budget. The measured creation path now
value-constructs every component, reserves generation/free-list capacity,
and publishes atomically; no `value_init_is_all_bits_zero` opt-in was needed.

### Verification

- Debug configure and full build: passed.
- Debug `ctest --output-on-failure`: 161/161 tests passed, including golden images,
  RPC scenarios, scene flow, and the WP47 immediate bind/write/raycast case.
- Dedicated lifecycle suite covers aligned string storage, middle/tail remove,
  move-only relocation, value initialization, populate/init rollback with
  resource counters, callback reentry, 4,095/4,096/4,097/100,000 batches,
  free/fresh mixing, generation stale classes, MAX retirement, capacity guard,
  deterministic LIFO reuse, and normal/exception teardown order.
- MSVC ASan configuration: `-DPELICAN_ENABLE_ASAN=ON`; the lifecycle suite
  passed under `/fsanitize=address`. The MSVC ASan runtime directory must be on
  `PATH` when invoking the test executable outside a Visual Studio developer
  shell.

## Design differences

- No lifecycle, ID, stale-policy, external-reference, or teardown semantics
  were intentionally changed from design v2.1.
- A Clang/GCC UBSan job was not run in this Windows/MSVC worktree. As allowed by
  the goal's environment exception, UBSan remains a CI follow-up; MSVC ASan does
  not provide undefined-behavior/alignment sanitization. Explicit 64-byte
  alignment assertions and MSVC ASan cover the local gate.
