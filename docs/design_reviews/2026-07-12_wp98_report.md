# WP98 完了レポート — アセット HR1 identity / transaction 基盤

## 結論

WP98 の GPU 非依存基盤を実装した。`AssetKey` を物理 path から切り離し、
`LogicalAssetId`、slot `generation`、`content_revision` を別概念として実装した。
logical resource table と reverse dependency index は単一の immutable snapshot に入り、
transaction group の commit 時に一回だけ atomic publish される。

実 texture/shader/model/material handler は追加していない。fixture の fake resource だけで、
parse all → validate all → stage all → topological commit、失敗時 rollback、
複数 logical table の frame-boundary barrier、旧 payload の DeletionQueue 接続点を検証した。

## 実装概要

- `AssetKey` は `project://` を正規化した project logical path と fragment の組である。
  store 名、絶対 path、volume/file identity は含めない。
- `WatchStore::logical_mount` から watcher の物理 relative path を project logical path へ戻す。
  宣言 mount を project tree の同一 logical path より優先し、local override が意味を変えない。
- `ResourceRegistry` は logical table、slot/free-list、source index、reverse dependency index、
  resource count、live bytes を一つの `ResourceRegistryState` に保持する。
- reader は `ResourceSnapshot` を一回取得して読む。writer は state copy に全変更を適用し、
  成功後に `atomic<shared_ptr<const State>>` を一回だけ差し替える。
- `ReloadCoordinator` は transaction group を queue し、`ReloadService::applyFrame()` から
  frame 先頭に適用する。無関係 group は独立で、一つの失敗が後続 group を止めない。
- `get_status.reload` の HR0 field (`state` / `epoch` / `error`) は維持し、
  `applied` / `failed` / `last_reload_error` を加算した。

## identity 遷移

```text
declare source A
  slot[0] generation=1, content_revision=1
  LogicalAssetId = pack(index=0, generation=1)
            │
            ├─ successful reload ×1000
            │    ID/index/generation は不変
            │    content_revision: 1 → 1001
            │
            ├─ failed candidate / validate / stage / publish
            │    ID/revision/payload/edge/count/live bytes は全不変
            │
            └─ destroy (slot[0] unbound、旧 ID は stale)
                  │
                  └─ redeclare source A (free slot reuse)
                       slot[0] generation=2, content_revision=1
                       新 LogicalAssetId。旧 generation=1 は拒否
```

`compatibility_revision` は rig/layout 等の互換性判定用であり、上図の slot generation と
`content_revision` のどちらにも連動させない。

## transaction と barrier

```text
ReloadCoordinator::enqueue(group)
        │
        └─ ReloadService::applyFrame (frame start)
              ├─ parse actor 0..N (全件)
              ├─ validate actor 0..N (全件)
              ├─ stage actor 0..N (全件、global ID 発行なし)
              ├─ dependency DAG を topological sort
              ├─ state copy 上で payload/revision/edge/count を更新
              ├─ atomic publish ── observer は old 全体か new 全体だけを見る
              └─ old payload → RetireSink
```

parse/validate/stage/topological sort/publish のどこかで例外になれば candidate/staged set だけを
破棄し、live state は publish しない。resource failure は status に記録する。

## HR1-T / HR1-M / HR2 の接続点

後続 handler は次の面だけを実装すればよい。

1. watcher の `ReloadRequest::key` と `ResourceSnapshot::reverseDependents()` から group を作る。
2. 各 resource actor に parse/validate/stage closure と group 内 `after` edge を登録する。
3. stage は resource 固有 candidate を `shared_ptr<const void>`、dependency key、
   compatibility revision、live bytes として返す。candidate 中は `declareResource()` を呼ばない。
4. GPU resource を持つ handler は `ReloadCoordinator::applyFrame(RetireSink)` の sink を
   `DeletionQueue::defer` へ適合させる。sink は atomic publish 後の所有権移譲であり throw しない。
5. HR1-T は texture table/descriptor actor、HR1-M は same-layout values actor、
   HR2-S/G は shader graph・pipeline・model/fragment actor を同じ group API に載せる。

これにより種別 handler は identity allocator、rollback、reverse edge barrier、status counter を
個別実装しない。実 shader poll の撤去、実 descriptor rebind、GPU upload、model instance rebuild は
それぞれの後続 WP に残している。

## fixture

`reloadtransaction_test` と `filewatcher_test` の WP98 section で以下を固定した。

1. project logical path + fragment の canonicalization と escape/absolute path 拒否
2. local override の選択 root だけが同一 `AssetKey` を供給すること
3. 同一 resource 1000 reload の logical ID 不変と revision 単調増加
4. destroy→redeclare の generation 増加と旧 handle stale
5. stage 途中失敗時の payload/ID/revision/edge/count/live bytes rollback
6. parse all → validate all → stage all の位相順と topological retirement
7. 二 logical table 1000 commit 中の並行 observer に half revision が見えないこと
8. HR0 status field 維持と resource counter/error の additive schema

## 境界

- 実 texture/material/model/shader resource の差し替えは未実装。
- HR0 の gate、watcher state machine、digest/reconcile protocol は変更していない。
- ECS generation と本 WP の logical resource generation は別型・別 table のまま。
- shader source/include graph と既存 poll の撤去は HR2-S、実 cross-file material transaction は
  HR2-S、GPU model/fragment staged commit は HR2-G の担当である。
