# WP206a completion report — stable material draw tag/filter

Date: 2026-07-26
Status: complete

## Outcome

The normal material-pass selection path no longer needs draw-call ordinals.
`pelican.material` entries can declare canonical string `tags`, and material
passes can declare `material_filter.include/exclude`. The filter is resolved
while compiling the immutable draw queue; the Vulkan execution loop consumes
only compact indirect ranges.

## Public contract

```json
{
  "name": "hero",
  "surface": "project://shaders/hero.surface",
  "tags": ["character", "outline"],
  "values": {}
}
```

```json
{
  "name": "outline_geometry",
  "type": "material",
  "material_filter": {
    "include": ["outline"],
    "exclude": ["hidden"]
  }
}
```

- `include` is any-match; an omitted or empty list accepts every material.
- `exclude` is any-match and takes precedence.
- Tags are non-empty strings of at most 255 bytes. Duplicate tags and
  include/exclude overlap are rejected.
- Canonical sorting makes authored list order irrelevant.
- Unknown tags are legal and are reported by resolution metadata.
- `material_range` remains a low-level compatibility control. If both controls
  are present, the ordinal range is applied after tag-filter compaction.

The v1 public identity is material-owned. Instance/draw-owned layers and
pass-local surface/render-state variants remain separate follow-up contracts.

## Data flow and ownership

1. `materialformat` parses and canonicalizes tags.
2. `materiallowering` and `MaterialInfo` preserve them through registration.
3. At each logical frame, `PolygonInstanceContainer` copies current registered
   tags into immutable `DrawItemSnapshot` values.
4. `Renderer` deduplicates active pass filters by stable fingerprint and sends
   them to every flat, sequential-XR, or multiview queue build.
5. `DrawQueueBuilder` resolves visibility-specific compact indirect ranges and
   publishes count/unmatched-tag metadata.
6. `MaterialRenderer` selects the compact range by numeric filter ID. No string
   comparison occurs in the Vulkan draw loop.

The stable ID is derived from canonical include/exclude lists plus
`pelican.draw_queue_builder.material_tag_filter@1`. A collision between
different canonical filters is rejected.

## Reload and observability

- Values-only material reload treats tags as structural data. A tag edit is
  rejected failure-atomically and the previous material/tag selection remains
  active.
- Structural material replacement is observed on the next immutable queue
  snapshot.
- Static frame-plan JSON records authored include/exclude, stable filter ID,
  pending state, and provenance.
- Runtime frame-plan JSON adds resolved draw count and unmatched
  include/exclude tags.
- `dump-lowered-material` prints tags only when present, preserving feature-off
  output bytes.

## Acceptance evidence

- Material registration order, input order, and draw-sort order invariance:
  `drawqueuebuilder_test`
- Include/exclude, empty/unknown/multiple tags, flat and two-view publication,
  empty-scene metadata: `drawqueuebuilder_test`
- Parser/lowering/runtime binding: `materialformat_test`,
  `materiallowering_test`, `materialbinding_test`,
  `renderingpass_helpers_test`
- Plan metadata and non-material rejection: `frameplanner_test`
- Preview preservation: `renderpipeline_resolve_test`
- Failure-atomic values-only reload: `materialvaluesreload_test`
- Full Debug build and all 899 CTest cases passed. The existing
  Windows symlink-permission-dependent PathResolver case was the only skip.

The feature-off representation is additive: untagged materials and passes
without `material_filter` retain the pre-WP206a queue and dump paths.

## Deliberate exclusions

- Instance- or primitive-owned selection layers
- Pass-local material surface/render-state variants and multipass routing
- GPU-authored selection or indirect arguments
- Shader-visible tag strings

The next dependent slice is WP206b: use this stable selection entry point to
dogfood a project-owned, duplicate-free pass-local material variant.
