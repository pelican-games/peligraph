# WP77 実装レポート: コンテナ K1 — `#` フラグメント参照の実ロード

日付: 2026-07-11
ブランチ: `agent/wp77-fragment-load`

## 実装概要

- 前任実装の `PathResolver` フラグメント解析・glTF 候補解決を引き継ぎ、既存 diff
  を基礎に未接続だった部分ロード経路を完成させた。
- `PathResolver::resolveExistingFileReference` を追加し、存在確認後も
  `ResolvedPathFragment` を保持する。従来の `resolveExistingFile` はフラグメントを
  引き続き拒否するため、既存利用者の意味論は不変。
- `asset_data.json` の `models[].path` と `SceneLoader::loadTransientGltf` から、
  解決済みパスとフラグメントを `GltfLoader` へ渡す。
- glTF/GLB の `mesh` / `node` / `material` / `animation` を名前またはフルパスで解決。
  短名の複数一致は候補フルパスを列挙し、同一フルパス重複・未知種別・未知名も
  参照名入りでエラーにする。インデックス参照は既存パーサどおり拒否する。
- `mesh` は対象 mesh の primitive、`node` は対象 subtree の mesh をロードし、親階層の
  transform を維持する。対象 primitive が参照する material と、その material が実際に
  使用する base-color / metallic-roughness / normal / emissive texture だけを登録する。
  tinygltf によるコンテナ全体の CPU parse は許容するが、未選択側の vertex buffer・
  material・texture は GPU 化しない。
- `material` は対象 material と texture 依存だけを登録し、primitive なしの material group
  として返す。現行 `ModelTemplate` に animation runtime 表現がないため、`animation` は
  名前解決と重複検証を行い、無関係な GPU resource を生成しない。
- フラグメントなしは従来と同じ登録・走査順（全 texture → 全 material → default scene
  node）を維持する。WP74 の RGBA8 mutable image と SRGB/UNORM 二 view を作る
  `MaterialContainer::registerTexture` 経路も変更していない。
- フラグメント付きの非 `.glb` / 非 `.gltf` 入力は、tinygltf parse 前に参照名入りで拒否する。

## テスト

`test/gltf_fragment_fixture.hpp` で 2 mesh / 2 material / 2 texture / node 階層 /
animation を持つ最小 GLB を生成し、次を `gltf_fragment_test` で確認した。

- 短い一意 mesh 名、mesh フルパス、node subtree、material、animation
- `asset_data.json` の `models[].path` からのフラグメント実ロードと、scene の
  `simplemodelview` による配置
- 選択 mesh で primitive が 1 個だけ生成され、GPU texture/material 登録数も対象依存分だけ
  増えること
- フラグメントなしでは 2 mesh ともロードされること
- 未知種別、未知名、曖昧短名（複数フルパス列挙）、同一フルパス重複、非 GLB
- `resolveExistingFileReference` が存在確認後もフラグメントを保持し、従来 API は拒否を維持
