## 1. 結論

`get_scene_revision` RPC と型付き service query を追加し、`SceneRevision`、
`preview_epoch`、最終 committed transaction、現在の preview lease を一つの軽量応答で
取得できるようにした。WP161 の coordinator が既に保証している preview epoch の増加規範は
変更せず、公開済みの epoch、preview result、journal record を service で集約した。

interactive の Object Tree / Inspector は 30 rendered frame ごとに watch token を poll する。
`scene_revision` または `preview_epoch` が変化した場合だけ既存の `refresh()` 経路を呼び、tree と
現在表示中の object を再 query する。他 actor の durable edit と live preview の開始・更新が
最大30 interactive frame以内に表示へ反映される。headless、RPC-only、replay、golden、XR の
deterministic driver は既存の callback gate の外側にあるため、query/enqueue trace 0 を維持する。

journal、projection transaction、projection adapters、schema 三 header、`.github`、DebugText、
UI layout、golden baseline は変更していない。未解決事項はない。

## 2. `get_scene_revision` 応答

preview open 後の応答例は次のとおりである。JSON の field 順も固定し、同じ
revision/epoch/state に対する二回の query が byte 一致することを fixture で確認した。

```json
{
  "scene_revision": 1,
  "preview_epoch": 1,
  "last_transaction": null,
  "preview_lease": {
    "actor": {
      "actor_id": 1,
      "display_name": "watch-actor"
    },
    "ticket": "preview-1",
    "affected_ids": [1],
    "state": "open"
  }
}
```

preview commit 後は `preview_lease` が `null` になり、同じ actor 情報と affected ID は durable
record から `last_transaction` へ移る。

```json
{
  "scene_revision": 2,
  "preview_epoch": 3,
  "last_transaction": {
    "actor_id": 1,
    "display_name": "watch-actor",
    "affected_authoring_ids": [1]
  },
  "preview_lease": null
}
```

production の frame-boundary commit は service wrapper ではなく WP161 coordinator hook を直接
呼ぶ。そのため pending preview result の enrichment は `get_scene_revision` の先頭で遅延同期し、
windowed/RPC production 経路でも open/update/commit/abort/forced-abort 後の状態を正しく返す。
fixture はこの production hook 相当の直接 commit 経路を使用した。watch 未読時も
`get_preview_result` または次の preview 操作で同期済み遷移を回収し、保留 metadata を蓄積しない。

## 3. epoch 遷移

初期 revision 1 から一連の遷移を行った結果を示す。preview 自体では revision は変わらず、
durable commit だけが revision を一回進める。

| 遷移 | scene_revision | preview_epoch | preview_lease | epoch 差分 |
|---|---:|---:|---|---:|
| 初期状態 | 1 | 0 | `null` | - |
| open | 1 | 1 | `open` | +1 |
| update | 1 | 2 | `updated` | +1 |
| commit | 2 | 3 | `null` | +1 |
| 次の open | 2 | 4 | `open` | +1 |
| abort | 2 | 5 | `null` | +1 |
| 次の open | 2 | 6 | `open` | +1 |
| forced-abort | 2 | 7 | `null` | +1 |

## 4. CAS が correctness boundary であること

V22-C2 の規範どおり、watch/polling は refresh latency の最適化であり、stale overwrite 防止の
correctness boundary ではない。fixture は revision 1 の commit を完了した後、
`get_scene_revision` を一度も読まずに別 field を古い `base_revision=1` で commit し、必ず
`stale_revision`（`current_revision=2`）になることを確認した。reject 前後で current revision は
2、journal は最初の一件のままである。したがって watch の遅延・欠落によって stale write が
通ることはなく、global SceneRevision CAS が安全性を担う。
