# WP150 実装レポート: STRUCT-SCHEMA0 — 共通 field descriptor + use-site policy

日付: 2026-07-18
ブランチ: `agent/wp150-schema0`

## 1. 実装概要

`EventPayloadSchema` に閉じていた member-pointer descriptor を、use-site に
依存しない型情報層と、用途ごとの policy 層へ分離した。

| 層 | 型・API | 責務 |
|---|---|---|
| 型情報 | `StructFieldType` / `StructFieldRange` / `StructFieldSchema` | field 名、scalar kind、型付き range、unit を共通表現する。Bool / Enum を共通 kind として持つが、各用途での許可は決めない。 |
| member 宣言 | `field<&T::member>()` / `StructFieldDeclaration` | member pointer から owner/member 型を導出し、名前・型・range・unit を結び付ける。Event / Behavior / Component の別 macro は作らない。 |
| field policy | `required(...)` / `defaulted(...)` | required/default を field ごとに明示する。Enum は `enumValue` / `enumValues` で canonical string と値を対応付ける。 |
| use-site policy | `EventPayloadPolicy` / `BehaviorParamsPolicy` / `ComponentPolicy` | Bool/Enum、required/default、decode/apply の許可範囲を用途別の型で固定する。 |
| schema 構築 | `structFields(policy, ...)` | policy 引数と全 field の `required/defaulted` を必須にする。policy 省略・暗黙 default・用途違反は compile error。 |

class definition 中は variant を直接構築せず POD descriptor を所有し、型完成後に
`StructFieldSchema` へ materialize する。これは WP71 で確認済みの MSVC 19.44 の
制約を維持するためである。Event の15-field descriptor は heterogeneous tuple を
保持せず、POD 配列だけを保持するため、従来の initializer nesting 上限も維持する。

## 2. use-site policy

### EventPayload

- 既存 `payloadFields(...)` は EventPayload use-site を名前で明示する互換 surface
  として保持した。
- 全 field を `Required` に固定し、Bool / Enum / default / optional を
  compile-time に拒否する。
- `PayloadFieldType` / `PayloadRange` / `PayloadFieldSchema` は共通型の alias とし、
  `EventPayloadSchema` の公開形、registry、validator、`load_json_payload` は変更して
  いない。
- unknown reject、unknown-before-missing、型/range validation、catalog/ref 一致、
  Typed/Payloadless/Opaque/Unknown 分類は従来経路をそのまま通る。

### BehaviorParams

- 全 field に explicit default を要求し、Bool / Enum を許可する。Enum field は
  canonical string 一覧の省略を compile-time に拒否する。
- JSON object の unknown key を先に検査し、default-constructed temporary に schema
  default を設定後、存在する key だけを decode/validate する。
- 全 field の型・整数精度・有限性・range・Enum 検証成功後だけ `noexcept swap` で
  destination へ publish する。途中失敗で live 値は変化しない。
- `StructFieldValidationError` が stable `StructFieldErrorCode` と `params.field` path を
  保持する。canonical encode も field 宣言順を保ち、不正な live 値を同じ code/path
  で拒否する。

### Component

- `componentPolicy(codec_name)` は空 codec 名を compile-time に拒否する。
- 各 field は `required(...)` または `defaulted(...)` を明示しなければならない。
- 本 WP は policy 機構までとし、実 component codec、scene loader、basic config には
  触れていない。実 codec は ED-CODEC0 の責務である。

## 4. WP150 追加 fixture

- runtime: policy 層分離、Behavior default/Bool/Enum/canonical roundtrip、failure atomicity
  と stable code/path、Event error precedence/load count（4 cases、70 assertions）。
- compile-pass: Event / BehaviorParams / Component の各 policy 1件。
- compile-fail: policy 省略、Event default、Behavior required、Behavior Enum mapping 省略、
  Component field policy 省略、Component codec 名省略の6件。
- 既存 WP71 fixture の source は変更していない。

## 5. 検証結果

1. Configure:
   `cmake -S . -B build -DSKIP_DEVSTUDIO=ON -DPython3_EXECUTABLE=%APPDATA%\uv\python\cpython-3.12.13-windows-x86_64-none\python.exe`
   — 成功。
2. Full Debug build: `cmake --build build --config Debug -j 6` — 成功。
3. Full ctest（直列最終 run）:
   `ctest --test-dir build -C Debug --output-on-failure -j 1`
   — 564 tests、失敗0。Windows の symlink privilege fixture 1件だけ既知 SKIP。
4. Golden inventory: `python test/golden_inventory.py --repo-root .` — PASS。
5. Golden verbose: `golden image cases match expected output` — 1 case、238 assertions、
   SKIP 0、byte baseline 一致。
6. Player: ctest が生成・検証した自己完結 project を使う通常 windowed hidden launch が
   8秒生存。確認後に停止し、本 WP の player process は残していない。
7. `git diff --check` — 問題なし。

検証上の注記: 最初の全 ctest では `rpc_scene_flow_headless_player` だけが、2回の
`get_status` に含まれる driver 管理の `VK_EXT_memory_budget` usage（約48 MB → 82 MB）
を deterministic 比較したため失敗した。schema/event 出力との差ではないことを
`LastTest.log` で確認し、GPU accounting の初期化後に同 fixture を単独 PASS、続く
全564件の直列 run も失敗0で完走した。対象外の scene fixture は変更していない。

`projects/example` の通常起動は配布外アセット（`AliciaSolid.vrm` など22件）がこの
worktree にないため fail-fast したので、player 8秒 smoke には全 ctest 内で生成済みの
light-only self-contained project を使用した。
