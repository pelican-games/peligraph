# WP194 完了レポート — append-only GPU registration transaction

日付: 2026-07-24

## 結果

render-config compilation が更新する GPU registry 群を
`RenderPipelineGpuRegistrationArena` の checkpoint-to-publication 区間へ束ねた。
target、buffer、compute task、shader、pipeline、fullscreen/debug/shadow/velocity pass の
いずれで後段処理が失敗しても、新規 registration membership は逆依存順に取り消される。
成功時だけ owner scope 付き manifest が runtime generation と同じ root へ公開される。

```text
resolve / logical + physical compile
  -> serialize legacy GPU registration interval
  -> checkpoint all registries
  -> prepare target / buffer / compute / shader / pipeline / pass
  -> build owner-scope GPU manifest
  -> prepare immutable runtime generation
  -> CAS publish runtime + GPU manifest
       success -> commit registration arena
       failure -> rollback every new registry membership
```

## registration arena

- `RenderTargetContainer`
- `FrameGraphResourceContainer`
- `ComputeTaskContainer`
- `ShaderLibrary`
- `PipelineFactory`
- `FullscreenPassContainer`
- `DebugDraw` / `DebugText`（provider 初回使用時に遅延 enlist）
- `ShadowDepthPassContainer`
- `VelocityPassContainer`

各 container は append-only registration log と checkpoint を持つ。登録関数は Vulkan
object を live table へ入れた後の name/log 更新で例外が起きても孤立 entry を残さない順に
変更した。pipeline rollback は新規 descriptor-set-layout cache entry も除去し、
shader rollback は reload unit、bundle reverse dependency、dirty list も復元する。

rollback 順は pass/descriptor、compute/buffer/target、pipeline/layout、shader とし、
参照側を先に破棄する。複数 config transaction が同じ mutable registry を同時に
checkpoint しないよう、この区間は直列化した。

## generation publication

`RenderPipelineRuntimeGeneration` は immutable `RenderPipelineGpuArena` を所有する。
scope は `render_pipeline/flat`、`render_pipeline/xr` 等の owner 名と、次の manifest を持つ。

- resource kind
- registry handle
- stable/diagnostic name
- buffer の declared bytes
- 将来の generation-owned registry 向け type-erased resource lease

prepare 中の arena は observer から不可視である。runtime root の CAS 成功時にだけ同時公開され、
`Renderer::currentFramePlanJson()` は arena generation、resource count、全 scope/resource を
出力する。XR mirror intermediate の登録も XR config transaction 内へ移した。

## 故障注入

実 Vulkan device 上で次の5点に fault を入れた。

1. render target 登録後
2. frame-graph buffer 登録後
3. compute task 登録後
4. fullscreen/debug-draw/debug-textを含む rendering pass 登録後
5. immutable runtime candidate 構築後、publish 前

各 fault 後に全対象 registry の registration count が基準値へ戻り、
`FrameGraphRuntimeContainer` に generation が公開されず、target/buffer/compute の
name lookup も失敗することを確認した。同じ process で全 fault を順に retry した後、
target、buffer、compute、fullscreen、debug、shader、pipeline を含む flat scope を
正常に generation 1 へ公開できる。

CPU-side transaction fixture では、candidate の resource lease が publish 前から
candidate と共に生存しながら active root には見えないこと、明示 rollback で解放されること、
既存 owner scope の重複が active root 不変のまま拒否されることを確認した。

## RPE10b2 へ残す境界

WP194 は append-only compatibility slice であり、pipeline hot reload 全体の完了ではない。

- legacy Vulkan object の実体は引き続き engine-owned registry にある
- 同じ owner scope の replacement/removal は未実装であり、重複を拒否する
- config から消えた pass/target/resource の generation 単位除去は未実装
- old frame が旧 Vk object を使い切る generation-owned resource lease は未接続
- submission fence 完了後の `DeletionQueue` retire は未接続
- FileWatcher / `ReloadGate` からの pipeline reload publication は未接続

次の WP195 / RPE10b2 では registry entry の ownership を owner scope generation へ移し、
same-name replacement と removal を一つの candidate として prepare する。旧 generation は
frame lease から旧 resource set を参照できるようにする。その後の RPE10b3 で submission
fence retire と watcher publication を接続する。
