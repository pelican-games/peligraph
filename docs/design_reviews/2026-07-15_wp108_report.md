# WP108 report — HR2-S shader/surface hot reload

Date: 2026-07-15

Status: complete and regression-tested

## Outcome

Shader hot reload now has one automatic input path: `FileWatcher`/`ContentDigest` feeds a
frame batch to `ReloadService`. The independent one-second `ShaderLibrary` mtime poll was
removed. Project and mounted-store GLSL, SPIR-V, includes, and `.surface` files use canonical
`AssetKey` identities and reverse dependencies.

One change prepares every affected define/pass variant, reflection result, dependent Vulkan
pipeline, and participating material layout/value payload before publication. A compile,
pipeline-create, surface-contract, JSON, or material-lowering failure discards the candidates and
keeps the complete previous generation live.

## Transaction path

1. `ShaderCompiler` returns the canonical physical files in the same conservative source graph
   used by the WP82 cache key. `ShaderLibrary` maps those files to project `AssetKey` values and
   tracks reload recipes per file or vertex/fragment surface pair.
2. `FileWatcher::applyFrameBatch` supplies all stable requests together. Per-request digests are
   committed only after the grouped result is known, so every member of a rejected shader/material
   transaction retries.
3. `ShaderLibrary::prepareReload` parses each changed surface once and compiles all reload units
   reached through the source/include/surface reverse index. Live bundles are not changed here.
4. `PipelineFactory::rebuildPrepared` temporarily exposes candidate bundles only while building
   all dependent pipeline candidates. It restores the live table before cross-domain validation.
5. `MaterialValuesReloadHandler::prepareSurfaceReload` permits parameter/layout changes within the
   fixed material custom-value buffer. It reparses and lowers every dependent material document,
   stages registry revisions and packed GPU values, and rejects descriptor/render-state contract
   changes that require a separate migration feature.
6. After every candidate succeeds, shader bundles, pipelines, material layouts/values, and logical
   registry payloads publish at the frame boundary. Replaced pipeline and pipeline-layout handles
   go through `DeletionQueue`. Render start consumes the publication and rebinds fullscreen inputs
   before command recording.

Manual/requested shader reload remains available through the runtime participant and forces every
tracked reload unit. Its periodic callback no longer scans timestamps; it only consumes a watcher
publication for renderer rebinding.

## Observability

`get_status.reload.runtime.pelican.shaders.details` reports:

- `source = file_watcher` and centralized gate state/reason;
- tracked reload units, bundles, and dependency keys;
- shader cache hits and misses accumulated by reload attempts.

Failures are copied to the affected live bundle logs and the runtime participant's last error
without changing its Vulkan module or version.

## Regression gates

- root and include edits reach all define variants; invalid GLSL keeps every prior version;
- `.surface` files now retain a physical source identity and all vertex/fragment variants replace
  together;
- repeated prepare demonstrates cache miss then cache hit behavior;
- real Vulkan `.surface + .material.json` parameter-layout changes publish together, while an
  invalid peer on either side rolls the entire group back;
- an old in-flight pipeline is queued for delayed destruction, fullscreen descriptors rebind after
  success, and do not rebind after a failed compile;
- batch digest results commit successful members and retry failed members;
- source-architecture checks reject restoration of the old ShaderLibrary polling route.

## Deliberate boundaries

- `engine://` embedded sources have no physical `AssetKey` and remain outside automatic file
  reload. Explicit forced reload only covers tracked file-backed units.
- Surface parameter declarations and shader code may change live. Texture/screen-input bindings and
  render state remain a descriptor/pipeline-description migration boundary and are rejected as one
  named transaction failure.
- Cross-file atomicity applies to stable requests coalesced into the same watcher frame. If an editor
  writes related files in separate frames, each frame remains independently valid and transactional.
