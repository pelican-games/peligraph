# WP156 E-HOST0 完了レポート

日付: 2026-07-18
対象ブランチ: `agent/wp156-ehost0`

## 1. 結論

windowed player が一つの stdio RPC 接続を bounded queue 経由で受け、engine thread の
frame boundary で既存 `RpcServer` / `EditorCommandService` に dispatch して応答を flush する
host 層を実装した。`--rpc` は headless では従来どおり blocking loop、windowed では新 host を
有効化する。

watch token、`preview_epoch`、編集 method、複数外部接続、WebSocket は実装していない。
loader / scene / ecs / behavior と schema 三 header、golden baseline には触れていない。
逸脱・未解決事項はない。

## 2. queue と frame boundary の設計

`WindowedRpcHost` は既定 capacity 64 の単一接続 queue を所有する。処理順は次のとおりである。

1. reader thread が stdin を行単位で読み、headless と同じく末尾 CR を除去して queue に入れる。
2. windowed loop は `updateFrameState()` 完了直後を commit 済み frame boundary とし、その時点の
   queue 全体を engine thread 側の local batch に swap する。swap 後に到着した行は次フレームまで
   handler に渡らない。
3. local batch を FIFO で `RpcServer::processLine()` に渡す。既存 JSON-RPC parse、strict reject、
   game-logic reload gate、method handler、`EditorCommandRpcAdapter` の規範をそのまま利用する。
4. 各 handler の完了後に response、改行、flush を同じ engine thread で行う。したがって受理済み
   query の応答が commit 前の途中状態を観測する経路はない。flat と XR の両 interactive path は
   共通の `update_interactive_state` から同じ boundary を通る。

queue 上限を超えた行は黙って破棄しない。queue 自体には入れられないため reader thread が output
mutex を取り、request ID を保持した次の安定 error を即時 flush する。

```json
{
  "code": -32000,
  "message": "windowed rpc request queue is busy",
  "data": {"reason": "busy", "queue_capacity": 64}
}
```

受理済み応答と busy 応答の write/flush は同じ output mutex で byte 単位に直列化する。
reader が終了済みなら host 終了時に join する。process-lifetime の `std::cin` で read が block 中の
場合は停止 flag と shared queue state を残して reader のみ detach し、window close を stdin EOF
待ちで停止させない。停止後に読取りが戻った reader は handler を呼ばず終了する。

## 3. stateful engine endpoint と headless 不変

既存 handler 登録列を `configureEngineRpcHandlers` にそのまま移し、modules、`instance_id`、pending
transform、`EditorCommandService` / adapter を `EngineRpcEndpoint` の session lifetime にまとめた。
windowed host は frame ごとに endpoint を作り直さないため、instance ID と pending state は一つの
外部接続中ずっと維持される。

headless は `EngineRpcEndpoint::run()` から従来の `RpcServer::run()` を呼ぶ。次の三重 gate で
byte 不変を確認した。

- `RpcServer::run()` の関数本文を `HEAD` と比較し、改行正規化後も全文一致
  (`RPC_RUN_SOURCE_EQUAL=True`、252 characters)。getline、CR 除去、改行、flush の本文に差分なし。
- WP156 fixture で同じ `get_status` / `scene_tree` 二行を headless blocking loop と windowed
  boundary の双方へ渡し、response stream の完全 byte 一致を確認。
- 全 CTest の既存 headless RPC integration（基本、camera、scene flow、input、event、XR demo）を
  無変更で全通過。golden / replay / strict parser の既存規範にも差分なし。

## 4. fixture

`windowedrpchost_test` に次の三つを追加した。

- capacity 2 に `get_status` と `scene_tree` を入れ、boundary 前は handler 0 回・output 0 byte、
  boundary 後は 2 回・headless と response bytes 一致。
- capacity 1 に三行を入れ、一行だけを boundary で処理し、残る二行がそれぞれ元の ID を持つ
  stable busy error になることを確認。
- headless `RpcServer::run()` が CRLF request に対して固定済み JSONL bytes を返す regression
  fixture。

focused 結果は 3/3 PASS である。
