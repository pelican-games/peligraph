# WP155 BEH0 — behavior attachment arena 完了レポート

日付: 2026-07-18
対象ブランチ: `agent/wp155-beh0`

## 1. 結論

WP155 BEH0 を完了した。behavior の正本を ECS component にせず、
engine-owned attachment arena として実装した。登録は宣言だけに限定し、
scene special binder、typed event、activation / pre-destroy barrier、callback 中の
structural mutation defer、owner cleanup、4 process 決定性 gate、自己完結 project
E2E までを追加した。

`communication/rpcserver`、凍結 schema 三 header、`src/core/ecs/` は変更していない。

## 2. 実装内容

### 2.1 公開 API と登録

- `Behavior` / `BehaviorContext` / `BehaviorAttachmentHandle` を追加した。
- `PELICAN_REGISTER_BEHAVIOR(Type, "stable_name", schema_version)` は
  factory、destroy、typed event thunk、既存 `BehaviorParamsPolicy` の schema、
  `RegistrationOwner` だけを登録する。static registration 時には instance を作らず、
  `onInit` も呼ばない。
- Params は既存の `StructFieldSchema` / `BehaviorParamsPolicy` をそのまま使用する。
  params 全省略時の全 default 適用と、I8/I16/I32/I64、U8/U16/U32/U64、
  F32/F64、String、Bool、Enum の canonical round-trip を fixture で固定した。

### 2.2 scene special binder

- SceneLoader は反復する `{"name":"behavior", ...}` を generic ECS component
  codec より先に収集し、宣言順のまま arena へ lower する。
- behavior-only object にも空 archetype の有効な EntityId を発行する。
- 同一 object の複数 behavior と同 type の複数 attachment を許可する。
- active DLL に存在しない type は object/type 名を含む hard error とする。
  DLL 未設定・未ロード時は raw component JSON を保持した pending attachment とし、
  type/object 名入り WARN を出す。

### 2.3 lifecycle、mutation、event

- scene publish 後の activation barrier で `attachment_seq` 順に factory / `onInit`
  を実行する。途中 fault 時は初期化済み instance を逆順 `onDestroy` して全体を
  rollback する。
- entity/component/parent/physics/render binding がまだ live な pre-destroy barrier で、
  entity ごとの attachment を逆順 `onDestroy` する。
- behavior callback 中の create/remove は次の behavior boundary へ defer する。
  update/event は handle snapshot を使い、各 snapshot の instance を最大一回だけ走査する。
- typed `onEvent(const Event&, BehaviorContext&)` は登録時 thunk で配送する。
  matching event type の active attachment だけを `attachment_seq` 順に呼ぶ。

### 2.4 owner 安全

GameLogicReloader の load failure、ABI failure、candidate unload、active unload、
reload failure、rollback failure を共通 cleanup 経路へ集約した。DLL を unload する前に、
owner の live behavior を逆順 destroy し、deferred mutation、game system、pending/frozen
queued event、behavior registration を purge する。

teardown 自体が失敗して旧 DLL がまだ load 済みの場合は、その同じ handle/owner を
再利用して rebuild する。二重 load による owner 不定を避け、rebuild も失敗した場合は
旧 owner を含めて unload/purge する。

## 3. B-C3 の実値

BEH0 で先に値を決定し、実装・設計本文・fixture を同じ値に固定した。

- stable name: **`"BehaviorSystem"`**
- literal order: **`50`**
- system total order: event/update とも **`(order, stable name)` 昇順**
- 同 order fixture の expected trace:
  - event: `A:event → B:event:one → B:event:two → Z:event`
  - update: `A:update → B:update:one → B:update:two → Z:update`
- scene `attachment_seq`:
  `(uint64_t(object declaration index) << 32) |
  uint32_t(component array index)`

これらは実装後の偶然の追認ではなく、BEH0 の規範値として
`docs/design_object_behaviors.md` に記載した。

## 4. 決定性と自己完結実証

- 専用 probe は同じ trace と `DeterministicRng` 結果を、fresh process 2回と
  `input_replay` process 2回で取得し、stdout byte の完全一致を検査する。
- 自己完結 project E2E は behavior-only object に同じ behavior type を2件宣言し、
  default/指定 params の `onInit`、`SceneLoaded` typed event、`onUpdate`、逆順
  `onDestroy` を実 player + game-logic DLL で確認する。

## 6. BEH2 への明示的持ち越し

B-C3 の undo/redo fixture は計画どおり BEH2 gate へ持ち越す。BEH0 では scene の
seq 決定則と system total order までを固定した。E-RPC1/BEH2 の authoring transaction
が導入された時点で、次を必須 fixture とする。

- undo restore は元 `attachment_seq` を復元する。
- redo も同じ seq を使う。
- runtime の新規 attach だけが新しい
  `(commit_seq, command_index, attachment_index)` を得る。
- forward → inverse → forward で seq 列と lifecycle/event/update trace が一致する。

BEH0 には存在しない undo/redo API を仮設せず、責務境界を維持した。
