# WP193 完了レポート — render pipeline runtime publication root

日付: 2026-07-24

## 結果

pass、frame graph、logical/physical plan、material route、sample-count、
variant policy、draw-sort provider選択を一つのimmutable
`RenderPipelineRuntimeGeneration`へ束ねた。
prepare中のcandidateは不可視であり、active rootはbase generation付きCAS一回で
差し替わる。rendererは一つのsnapshotを論理フレームの全viewで保持する。

```text
compiled pass + FramePlan + CompiledRenderPipeline + VulkanTargetPlan
  -> prepareGeneration()
  -> PreparedRenderPipelineGeneration (inactive)
  -> validate pass/node/barrier/route bindings
  -> compare_exchange(active root, base generation)
  -> RenderPipelineRuntimeGeneration N
       -> frame shared lease
       -> retire N-1 after last reader
```

## publication contract

- `CompiledRenderProgram`が同じrendering-pass IDに対するcompiled passとframe graphを
  同居させる。rendererは別containerから二度引きして組み合わせない。
- `RenderPipelineRuntimeGeneration`はenabled feature、ordered pass ID、name table、
  program tableをimmutable rootとして所有する。
- `PreparedRenderPipelineGeneration`はmove-onlyで、publishまたはrollbackまでactive stateへ
  影響しない。
- publishはcandidateのbase generationとactive generationが一致する場合だけ成功する。
  stale candidateとCAS raceはlive rootを変更しない。
- 同名programはIDを維持し、新しいflat/XR variantはordered table末尾へ追加する。
- `FrameGraphRuntimeContainer`とlegacy `RenderingPassContainer` facadeは同じ
  `RenderPipelineRuntimePublication`を共有する。facadeを別操作でpublishしない。
- compatibility `find()`はgenerationをownerとするaliasing `shared_ptr`を返す。

## frame integration

`Renderer::renderLogicalFrame()`は論理フレーム開始時にgeneration snapshotを一度取得する。
GPU timingのnode capacity、compiled pass、frame graph、sample/target plan、
draw-sort provider選択、graph variant、projection jitter、各viewの実行はすべてそのrootから読む。
途中で新rootがpublishされても当該フレームは旧rootを完走し、次フレームから新rootを見る。

`currentFramePlanJson()`には`runtime_generation`を出力する。診断dumpがどのpublicationを
観測したかをroute/sample/physical planと一緒に追跡できる。

## RPE10bへ残す境界

WP193はRPE10のruntime publication rootであり、pipeline hot reload全体の完了ではない。

- render target / frame-graph buffer / compute taskのregistryはまだgeneration外
- fullscreen/material `VkPipeline`やdescriptor/targetのcandidate arenaは未実装
- same-name reload中のGPU registry mutationをrollbackするfault-injection fixtureは未実装
- configから消えたprogramをflat/XR owner scope単位で除去する規則は未実装
- old Vulkan objectをsubmission fence完了後に`DeletionQueue`へ渡すretireは未実装
- FileWatcher / `ReloadGate`からpipeline prepare/publishを起動する経路は未接続
- 実draw-sort provider generationは`RenderPolicyRegistry`のqueue構築時leaseで保護され、
  rootが原子的に所有するのはcompiled policy内のprovider名まで

次段RPE10bでは、GPU registry snapshotをgenerationへ所有させるか、generationが参照する
candidate arena handleを導入する。prepare failureでlive GPU state/count/bytesが不変、
成功publish後もin-flight frameが旧resourceを使い切れることを先にfixture化する。
