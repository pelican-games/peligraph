# WP113 着手停止レポート

日付: 2026-07-16
対象: WP113 — T-TAA 標準 TAA feature（ユーザー空間 stdlib）

## 結論

WP113 の実装には着手していない。`docs/implementation_plan.md` の WP113 と
`docs/design_taa_jitter.md` v2.1 §2 が要求する数値 feature parameter を、
WP112 で公開された機構だけでは shader へ配送できないためである。

目標ファイルの絶対条件は「J1 の公開機構で不足があれば実装せずレポートに質問」
である。このため、エンジン本体へ非公開の配線を追加したり、固定値へ読み替えたり
せず停止した。

## 不足している公開機構

要求されている公開値は次の 3 個である。

| parameter | 既定値 | 用途 |
|---|---:|---|
| `alpha` | `0.1` | `mix(clamped_history, current, alpha)` の新フレーム寄与率 |
| `disocclusion_tau` | `0.1` | 相対深度差による履歴棄却閾値 |
| `depth_epsilon` | 要決定 | 相対深度差の分母を安定化する下限 |

一方、WP112 の `pelican.render_feature_parameters` version 1 が宣言できるのは
`render_targets` だけである。`src/project/featurecompose.cpp` の
`parseRenderTargetParameters` は宣言 object の `schema`、`version`、
`render_targets` 以外を unknown field として reject する。

feature instance の `parameters` も render-target 名を表す string だけを受理する。
`bindFeatureRenderTargets` は宣言されていない parameter を unknown parameter、
非 string 値を `binding must name a render target` として reject する。このため、
例えば次の必要な形は現行公開 schema では compose できない。

```json
{
  "ref": "engine://features/taa.json",
  "parameters": {
    "scene_color": "lit_color",
    "velocity": "velocity",
    "depth": "offscreen_depth",
    "downstream_color": "lit_color",
    "alpha": 0.1,
    "disocclusion_tau": 0.1,
    "depth_epsilon": 0.00001
  }
}
```

fullscreen pass が利用できる push constant も既定の
`none` / `camera_position` / `projection_view` に限定され、feature instance の任意
数値を渡す ABI はない。`shader_defines` は feature 全体の boolean macro 名の列で、
instance parameter の数値配送経路ではない。

## 実装可能な部分と停止理由

次の部分は WP112 の公開機構だけで実装できることを確認した。

- scene color、velocity、depth、downstream color の named render-target binding
- `taa_accum` の history render target と二 fullscreen pass
- depth target の `SAMPLED` usage override
- FrameUBO の jitter / epoch pair を用いた reset 判定
- four-input resolve、current accumulation の composite

しかし、数値 3 値を shader 内の固定 `const` にすると「feature params 公開」を
満たさない。ユーザーが同梱 shader をコピーしてソースを書き換える方法は stdlib の
改造手順にはなるが、project の feature instance parameter ではない。既定値だけを
固定して先へ進むのも、受け入れ条件の読み替えになる。

## 質問

次のいずれを WP113 の正とするか決定が必要である。

1. J1 の後続修正として、version 付き scalar feature parameter 宣言と shader への
   配送 ABI（専用 UBO、汎用 fullscreen parameter block、または値付き compile-time
   specialization）を先に追加し、その後 WP113 を実装する。
2. WP113 v1 に限り `alpha`、`disocclusion_tau`、`depth_epsilon` を TAA shader 冒頭の
   コピー・改造可能な定数として公開したものと見なし、instance parameter 化は後続
   WP に分離する。
3. 別の既存公開機構を使用する。使用すべき schema と shader 配送経路を指定する。

選択肢 1 はエンジン C++ 変更を伴うため、現 WP の排他条件からは実施できない。
選択肢 2 はエンジン変更なしで実装可能だが、現行の「feature params 公開」からの
明示的な仕様変更が必要である。

## 変更・検証状況

- feature JSON / shader / golden: 変更なし
- build / ctest / player: 実装未着手のため未実施
- 特権的機構の追加: なし
