# WP200 完了レポート — fullscreen PassImplementation provider

日付: 2026-07-24

## 結果

同じlogical contractを満たすpass実装の差し替えを、graph transformやVulkan backend
拡張から独立した公開境界として実装した。最初のv1はfullscreen passのvertex /
fragment shader referenceだけを返せる。builtin identity providerとgame DLL providerに
特権差はなく、どちらも同じowner-aware registryとtyped callbackを通る。

```text
authoring pass JSON
  implementation.provider (optional)
              |
              v
VulkanTargetPlan内のlogical node + authored fullscreen interface
              |
              v
pelican.render.fullscreen_pass@1
  typed ports / relations / access / intent / footprint(+radius)
  interface flags / stable fingerprint
              |
              v
PassImplementationProviderV1
  output: implementation id + vertex/fragment shader refs only
              |
              v
PassImplementationSelection provenance
              |
              v
existing runtime shader/pipeline compiler
```

## 公開ABIと契約

`render/pass_implementation_abi_v1.hpp`はC ABI越境可能なstandard-layout /
trivially-copyable descriptorだけを公開する。入力stringとarrayはcallback中だけ有効で、
providerは保持しない。出力stringは入力rangeをaliasしてよく、それ以外はprovider
unregisterまで有効なimmutable storageに置く。engineはregistry leaseを解放する前に
copyする。callbackは将来の並行呼び出しを許容する実装とし、同じleaseを待つ
register / unregisterをcallback内から再入しない。

contractには次を含む。

- `pelican.render.fullscreen_pass@1`という版付きcontract id
- pass名とfullscreen kind
- canonical logical type-pattern JSONとport relation JSON
- input/output direction、read/write、access intent
- `same_pixel` / `neighborhood` / `arbitrary` / `temporal`と任意radius
- camera position / projection-view push constant、light-data interface flag
- pass名を除いたstable fingerprint

provider出力は版付きimplementation idとshader pairだけである。logical port、
resource use、push constant、light-data、effect、physical representation、Vulkan
handleは変更できない。

## 選択、診断、failure atomicity

fullscreen pass JSONは次を任意指定できる。

```json
"implementation": {
  "provider": "game.custom_composite"
}
```

未指定時は`builtin.fullscreen_v1`がauthoring shaderをそのまま返す。明示providerが
見つからない場合はbuiltinへ暗黙fallbackしない。provider envelope、owner、
generation、capability、callback status、output descriptor、implementation id、
shader rangeをengine側で検証し、provider名とpass名を含むerrorにする。
通常のlogical render nodeに加え、エンジン常設の`output_transform`もruntime実装が
fullscreen shader pairなので同じtyped contract / builtin identity経路を通す。
専用logical node kindは維持されるため、terminal構造と色invariantは変更されない。

複数fullscreen passのcallback結果は一時配列へ解決し、全件成功後だけ
`PassDefinition`へ反映する。後段passの失敗で先行passだけが差し替わる状態は作らない。
選択結果はprovider owner / handle identity / generation / version / capabilityと
contract fingerprintを含む`PassImplementationSelection`としてruntime compiled passまで残る。

## publicationとhot reload

flat / preview / XRをまとめてprepareするrender-config transactionは、一つのimmutable
provider registry snapshotを全variant解決からpublication CASまで保持する。game DLLの
owner releaseはexclusive lockを取得するため、in-flight compile snapshotが終わるまで
registrationとcallback codeをretireしない。

既存game-DLL fixtureへpass providerを追加し、draw-sort providerと同じreload transactionで
次を確認した。

- generation 1はV1 fragment shaderを返す
- reload成功後のgeneration 2はV2 fragment shaderを返す
- ABI不正candidateはgeneration 2を維持する
- prepared rebuild failureは旧ownerを再activateしV2を維持する
- shutdown後はgame providerが解決不能になる

snapshotによるowner release待機はローカルregistryの専用並行testで固定した。candidate DLLの
事前登録自体もexclusive mutationなので、reload E2Eでcompile snapshotを人工的に保持して
旧DLL解放だけを測る構造にはしていない。

## 後続

v1はshader pair差し替えだけなので、target planning後・runtime shader compilation前に
解決しても物理計画を変えない。implementation applicabilityやplanning constraintが必要に
なった時はtarget compiler前の別版境界として設計する。

次はRPE11bとしてtagged region / subgraph replacementを実証する。global
`GraphTransform`とrenderer-wide `RenderStrategy`もそれぞれ別fixtureとし、一つの万能
provider callbackへ統合しない。
