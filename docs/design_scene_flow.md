# シーン遷移と非同期ロード(v1)

対象読者: エンジン担当。
ステータス: v1 ドラフト(2026-07-08。レビュー前)。
前提: `design_scene_format.md`(複数シーン/1 ファイルが標準形)、
`design_game_logic_native.md`(GameContext)、コマンド層 stage 3。

## 0. 目的

scene v1 は複数シーンを標準形としたのに、実行時にシーンを切り替える手段が
ない(起動時に 1 回構築されるだけ)。「1 シーンのデモ」から「複数シーンの
ゲーム」への境界線を越える。2 段階: S1 = 同期切替、S2 = 非同期ロード。

## 1. S1: 同期シーン切替

- API: `GameContext::loadScene(name)` / rpc `load_scene {name}` /
  `GameContext::currentScene()`。宛先 = プロジェクトのシーンデータ内の
  シーン名(scene v1 の複数シーン)。未知名は名前入りエラー
- 意味論: **全 GameObject 破棄 → 新シーンを既存バインダ経路で構築**
  (light / collider / camera / material — 起動時構築と同じコードパスを
  通すこと。切替専用の第 2 経路を作らない)
- 呼び出しタイミング: ゲームシステムの update 中に呼ばれたら**フレーム末尾で
  実行**(イテレーション中の全破棄事故を防ぐ。予約 → フレーム境界で適用)
- EngineTime は継続(frame_index・時間はリセットしない)。シーンローカル時間が
  欲しければゲーム側で currentScene 切替時刻を覚える
- rpc 運用: `get_status` にシーン名を追加。load_gltf(stage 3)の一時ロード
  オブジェクトはシーン切替で破棄される(明文化)

## 2. S2: 非同期ロード(将来 WP)

- 解釈層(pelican_project)は純ロジックなので**別スレッドで安全に走らせられる**
  (分離設計の配当)。パース・検証・パス解決をワーカで実行
- GPU アップロードはフレーム分割(1 フレームあたりの転送量上限)
- API: `loadSceneAsync(name)` → `isLoading()` / 完了通知はイベント層
  (`design_event_layer.md`)の `scene_loaded` を予約
- プリロード宣言(project.json で隣接シーンの先読み)は需要が出てから
- フェード等の遷移演出はゲーム側/2D 機能の領分(エンジンは状態だけ提供)

## 3. 検証

- S1: rpc 結合テスト — load_scene → capture が切替前と PNG 相違 + 決定性
  (2 回実行一致)+ 未知名エラー + get_status のシーン名。
  golden は増やさない(シナリオテストで足りる)
- 切替を N 回繰り返してリーク・ハンドル残留がないこと(オブジェクト数 assert)

## 4. 未決事項

1. シーン名の名前空間: シーンファイルが複数ある場合の修飾(`file:scene`)。
   v1 は全ファイル横断のフラット名 + 重複は起動時エラー、で開始
2. 「残留オブジェクト」(シーンをまたいで生きる、プレイヤー等)の指定。
   v1 はなし(ゲーム側でセーブ/再構築)。需要が出たら persistent フラグ
3. S2 のスレッド境界(Vulkan キュー所有権・転送キュー)は着手時に詳細化
